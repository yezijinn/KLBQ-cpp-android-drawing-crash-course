# 第 27 章 · 编译四步与链接：链接器在做什么

> [!abstract] 本章目标
> 拆开链接器，理解符号解析和重定位这两件事。
> 第 03 章走过流程，本章讲内核；第 28 章讲静态库，第 30 章讲分析工具。

> [!note] 承上
> 卷一第 03 章走过"预处理→编译→汇编→链接"四步的流程。
> 本章深入最后一步——**链接器到底干了什么**（符号解析 + 重定位）。

## 先看一个 .o 里有什么

```c
// demo.c
#include <stdio.h>

int global_init = 42;        // .data
int global_zero;             // .bss
const char *msg = "hi";      // .rodata

int add(int a, int b) { return a + b; }     // 已定义

int main(void) {
    printf("%d\n", add(1, 2));
    return 0;
}
```

> [!note] `nm` 是什么
> `nm` 是 **binutils 里的"符号表查看器"**——列出目标文件/可执行文件里所有的函数和变量（符号），
> 以及它们的地址和类型（`T`=代码、`D`=已初始化数据、`U`=未定义……）。
> ```bash
> nm demo.o        # 看 demo.o 的符号
> nm -C app        # -C 把 C++ 修饰名还原成可读形式
> ```
> **判断"某个函数到底定义没定义"就用它。** 第 30 章会系统讲 `nm`/`objdump`/`readelf` 三件套。

```bash
gcc -c demo.c -o demo.o
nm demo.o
```

输出：

```
0000000000000000 D global_init
0000000000000004 C global_zero
0000000000000000 R msg
0000000000000000 T add
000000000000001a T main
                 U printf          ← U = undefined，未定义
```

`U printf` 是关键：**编译单元知道有 printf 这个函数，但不知道它在哪。**
找它的工作由链接器完成。

## nm 输出的字母含义

| 字母 | 含义 |
|---|---|
| `T` / `t` | 代码段符号（大写=全局，小写=局部） |
| `D` / `d` | 已初始化数据段 |
| `B` / `b` | BSS 段（未初始化） |
| `R` / `r` | 只读数据段 |
| `C` | Common 符号（未初始化的全局变量） |
| `U` | **未定义**（需要外部提供） |
| `W` | 弱符号 |

## 链接器的两件事

### 第一件：符号解析（Symbol Resolution）

把每个 `U` 符号，在其它 `.o` 或库里找到唯一的定义。

```
main.o:   U printf   ──┐
                       ├──→  在 libc 里找到 printf 的定义  ✓
demo.o:   U printf   ──┘

找不到 → undefined reference to `xxx'
找到多个且都不是弱符号 → multiple definition of `xxx'
```

### 第二件：重定位（Relocation）

`.o` 里调用 `printf` 的位置，地址是**空的（填 0）**。
链接器知道 `printf` 的最终地址后，把这些空位补上。

反汇编 `.o` 看看：

```bash
objdump -d demo.o
```

```
  1a:   bl      0 <main+0x2c>        ← 跳转到 0？明显是占位
        1a: R_AARCH64_CALL26  printf    ← 重定位项：这里要填 printf 的地址
```

`R_AARCH64_CALL26` 是重定位类型，意思是"把这个 bl 指令的目标地址改成 printf 的地址"。

链接后：

```bash
gcc demo.o -o demo
objdump -d demo | grep -A2 '<main>'
```

```
  4005a4:   97ffffb0    bl  400464 <printf@plt>
```

地址填上了。

## 重定位表

```bash
readelf -r demo.o
```

```
Relocation section '.rela.text' at offset 0x... contains 3 entries:
  Offset          Info           Type            Sym. Name
  00000000001a  000b0000011b  R_AARCH64_CALL26  printf
  000000000024  000c0000011b  R_AARCH64_CALL26  add
```

每一项告诉链接器：
- **Offset**：要改的位置（在哪个节的哪个偏移）
- **Type**：怎么改（填绝对地址？相对偏移？）
- **Symbol**：改成谁的地址

## 常见的重定位类型（ARM64）

| 类型 | 用途 |
|---|---|
| `R_AARCH64_CALL26` | `bl` 指令跳转目标（±128MB 范围） |
| `R_AARCH64_JUMP26` | `b` 指令跳转目标 |
| `R_AARCH64_ADR_PREL_PG_HI21` | `adrp` 指令（页对齐地址高 21 位） |
| `R_AARCH64_ADD_ABS_LO12_NC` | `add` 指令（页内低 12 位） |
| `R_AARCH64_ABS64` | 64 位绝对地址（数据段里的指针） |
| `R_AARCH64_RELATIVE` | 相对基址的重定位（PIE 用） |

前四个组合起来就是"访问一个全局变量"：

```asm
adrp    x0, global_init        // 取变量所在页的基址
add     x0, x0, :lo12:global_init   // 加上页内偏移
ldr     w1, [x0]               // 读值
```

## 符号表结构

```c
typedef struct {
    uint32_t st_name;      // 名字在字符串表里的偏移
    uint8_t  st_info;      // 类型 + 绑定属性
    uint8_t  st_other;     // 可见性
    uint16_t st_shndx;     // 属于哪个节（SHN_UNDEF=未定义）
    uint64_t st_value;     // 值（通常是地址/偏移）
    uint64_t st_size;      // 大小
} Elf64_Sym;
```

`st_info` 拆成两半：

```c
#define ELF64_ST_BIND(i)   ((i) >> 4)      // 绑定：GLOBAL/WEAK/LOCAL
#define ELF64_ST_TYPE(i)   ((i) & 0xf)     // 类型：FUNC/OBJECT/SECTION
```

| 绑定 | 值 | 含义 |
|---|---|---|
| `STB_LOCAL` | 0 | 只在当前文件可见（`static`） |
| `STB_GLOBAL` | 1 | 全局可见 |
| `STB_WEAK` | 2 | 弱符号（可被覆盖，找不到也不报错） |

| 类型 | 值 | 含义 |
|---|---|---|
| `STT_NOTYPE` | 0 | 未指定 |
| `STT_OBJECT` | 1 | 数据（变量） |
| `STT_FUNC` | 2 | 函数 |
| `STT_SECTION` | 3 | 节 |

## 强符号与弱符号

C 语言规则：

- 已初始化的全局变量 = **强符号**
- 未初始化的全局变量 = **弱符号**（Common）
- 函数定义 = 强符号
- `static` = 内部符号，不参与冲突

```c
// a.c
int x = 10;        // 强

// b.c
int x;             // 弱 → 链接后指向 a.c 的 x
```

两个强符号同名 → `multiple definition` 错误。

```c
// a.c
int x = 10;        // 强
// b.c
int x = 20;        // 强 → 报错
```

**本项目为什么用 `= delete` 而不是弱符号？** 因为弱符号意味着"找不到也放行"，
运行时才崩；`= delete` 是编译期就报错。能早发现就不要晚发现。

> [!note] `__attribute__((...))` 是什么
> 它是 **GCC/Clang 的"扩展语法"**——用来给函数、变量附加"编译器才知道的属性"。
> 格式固定：`__attribute__((属性名))` 写在声明的前面或后面。
> ```c
> __attribute__((weak))  void f(void);     // 弱符号（本节的例子）
> __attribute__((aligned(16))) int x;      // 16 字节对齐（第 07 章见过）
> __attribute__((noreturn)) void die(void); // 告诉编译器"这函数不返回"
> ```
> **它不是标准 C/C++，是编译器扩展**（MSVC 用 `__declspec(...)`，写法不同）。本项目用 GCC/Clang，所以是这套。

## `__attribute__((weak))` 的实战用法

允许"有就用，没有就算了"：

```c
__attribute__((weak)) void on_hit(void *regs) {
    // 默认空实现
}

// 调用方
if (on_hit) on_hit(regs);       // 如果别处定义了强符号，就用那个
```

本项目断点结构里的函数指针是另一回事（那是数据字段，不是符号），
但概念相通：**留一个可被替代的默认实现**。

## 静态链接 vs 动态链接

| | 静态链接 | 动态链接 |
|---|---|---|
| 时机 | 编译时全部打包 | 运行时才加载 |
| 产物大小 | 大 | 小 |
| 启动速度 | 快（不用找库） | 略慢 |
| 库更新 | 要重新编译 | 换 .so 即可 |
| 依赖 | 无 | 必须有对应 .so |

本项目：

```
ImGui、VulkanGraphics、PhysX      → 静态（源码/.a 编进 exe）
liblog.so libandroid.so libz.so   → 动态（-llog -landroid -lz）
libvulkan.so libgui.so libutils.so → 运行时 dlopen（可选依赖）
```

`LOCAL_LDLIBS := -llog -landroid -lz` 就是动态链接。

> [!tip] 为什么 vulkan 不直接链接？
> 因为不是所有 Android 设备都有 Vulkan。
> 如果静态/动态链接 `libvulkan.so`，在没有它的设备上程序**根本无法启动**。
> 用 `dlopen` 动态加载，可以在运行时判断：有就用，没有就降级。
> 这就是 `vulkan_wrapper.cpp` 存在的意义（第 60 章）。

## 链接顺序（重点）

```
gcc main.o math_utils.o -o app     ✓
gcc math_utils.o main.o -o app     ✗（可能失败）
```

传统 GNU 链接器**从左到右**扫描：
- 维护一个"未解决符号"集合
- 遇到库/目标文件，用它的定义去解决集合里的符号
- 它的新需求加入集合，只能靠**右边**的文件解决

所以：**依赖方在左，被依赖方在右。**

循环依赖的解法：

```bash
gcc a.o b.o a.o -o app          # 重复列一次
gcc -Wl,--start-group a.o b.o -Wl,--end-group -o app   # 或分组
```

本项目的静态库顺序（`Android.mk`）：

```makefile
LOCAL_STATIC_LIBRARIES := \
    embree_prebuilt \
    lexers_prebuilt \
    math_prebuilt \
    sys_prebuilt \
    task_prebuilt \
    simd_prebuilt
```

Embree 内部有依赖（lexers 依赖 sys/sys 依赖 math 等），
顺序错了就会出现满屏 `undefined reference`（第 28 章详述）。

## 动手：制造并修复链接错误

> [!tip] Windows 用户怎么办
> `gcc`/`nm`/`objdump` 在 **Git Bash（w64devkit）里都有**，本练习可直接在 Windows 上做。`readelf` 需 WSL。

```bash
# 1. 未定义符号
cat > u.c << 'EOF'
extern int missing_func(void);
int main(void) { return missing_func(); }
EOF
gcc u.c -o u
# 输出：undefined reference to `missing_func'

# 2. 重复定义
cat > d1.c << 'EOF'
int shared = 1;
int main(void) { return 0; }
EOF
cat > d2.c << 'EOF'
int shared = 2;
EOF
gcc d1.c d2.c -o d
# 输出：multiple definition of `shared'

# 3. 链接顺序
cat > m.c << 'EOF'
int helper(void);
int main(void) { return helper(); }
EOF
cat > h.c << 'EOF'
int helper(void) { return 0; }
EOF
gcc h.c m.c -o mh      # 可能失败（旧版 ld）
gcc m.c h.c -o mh      # 成功
```

每条错误信息都要能读懂，说出它对应本章的哪个环节。

## `undefined reference` 的三种成因（对应导航承诺）

看到 `undefined reference to 'xxx'`，按概率排查三种原因：

| # | 成因 | 症状特征 | 排查 |
|---|---|---|---|
| 1 | **源文件没加到构建** | 报错符号是你自己写的函数 | 检查 `LOCAL_SRC_FILES` / Makefile 是否漏了该 `.cpp` |
| 2 | **库没链接** | 报错符号来自第三方/系统库 | 检查 `LOCAL_STATIC_LIBRARIES` / `-lxxx` |
| 3 | **链接顺序错** | 库都加了还报错 | 库放**目标文件之后**（第 28 章）|

**定位工具**：`nm -u app.o` 列出这个 `.o` 需要哪些符号，逐个确认谁能提供。

> [!tip] 记忆口诀
> "**漏文件、漏库、顺序错**"——三种成因按这个顺序排查，90% 的 undefined reference 都能定位。

## 课后习题

### 习题 27.1 制造并修复三类链接错误（★★）

**要求**：依次制造"未定义符号""重复定义"两种链接错误并修复。

**验证方式**：每制造一个错误，确认报错文本包含对应关键词（`undefined reference` / `multiple definition`），修复后能编译通过。

**① 未定义符号**：

```c
// u.c：调用了一个没定义的函数
extern int missing_func(void);
int main(void) { return missing_func(); }
```

```bash
gcc u.c -o u
# 报错：undefined reference to `missing_func'
```

**② 重复定义**：

```c
// d1.c
int shared = 1;
int main(void) { return 0; }
// d2.c
int shared = 2;
```

```bash
gcc d1.c d2.c -o d
# 报错：multiple definition of `shared'
```

**修复**：
① 补上 `missing_func` 的定义（或链接含它的库）；② 只在一处定义 `shared`，另一处用 `extern`。

> [!note] 编译错误 vs 链接错误
> - **编译错误**：语法/类型问题，编译器直接报（`expected ';'`）。
> - **链接错误**：语法都对，但"找不到符号"或"重复定义"——发生在最后一步链接。
> 看到 `undefined reference` / `multiple definition` 就知道是链接阶段。

### 习题 27.2 用 `nm` 查看符号表（★）

**要求**：编译一个 `.o`，用 `nm` 看 `U`（未定义）和 `T`（代码）符号。

**验证方式**：`nm m.o` 的输出里，`add` 应标 `T`（已定义代码），`printf` 应标 `U`（未定义，待链接）。若某个函数你明明定义了却标 `U`，说明它没被编进这个 `.o`。

```bash
echo 'int add(int a,int b){return a+b;} int main(){return add(1,2);}' > m.c
gcc -c m.c -o m.o
nm m.o
# 会看到：
#   T add      ← 定义的函数（代码段）
#   T main
```

> [!tip] `nm` 的三列
> 地址、类型、名字。`T`=代码、`D`=已初始化数据、`U`=未定义（需外部提供）。
> 判断"某个函数到底定义没定义"就用 `nm`（第 30 章详解）。

## 常见坑排查表

| 症状 | 最可能的原因 | 解法 |
|---|---|---|
| `undefined reference to 'xxx'` | 没链接库/漏源文件/顺序错 | `nm -u` 查缺什么；库放后面 |
| `multiple definition of 'xxx'` | 头文件里定义了全局变量 | 头文件只放 `extern`，定义放 `.cpp` |
| Linux 报 `main`，Windows 报 `WinMain` | 平台入口名不同 | 都表示"找不到入口" |
| `.o` 编过但链接失败 | 依赖库没给 | 补 `-lxxx` |
