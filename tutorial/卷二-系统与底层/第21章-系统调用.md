# 第 21 章 · 系统调用

> [!abstract] 本章目标
> 理解用户态如何向内核请求服务，能直接用 `syscall()` 写一个 hello world。
> 第 74 章的 `process_vm_readv` 就是本章的直接应用。

> [!note] 承上
> 前面几章都在讲"用户态看到的程序"。
> 本章揭开底：**用户态想请内核帮忙（读文件、发网络包），走的是什么路——系统调用**。

## 先看一个不用 printf 的 hello world

```c
#include <unistd.h>
#include <sys/syscall.h>

int main(void) {
    const char *msg = "Hello from syscall\n";
    // syscall(调用号, fd, buf, count)
    syscall(SYS_write, 1, msg, 20);
    syscall(SYS_exit, 0);
    return 0;
}
```

编译运行，屏幕上照样出现文字。
这证明了一件事：**`printf` 本身不是系统能力，它只是对 `write` 系统调用的包装。**

## 用户态与内核态

CPU 有两种执行级别（以 ARM64 为例，EL0 / EL1）：

| 级别 | 名称 | 能做什么 | 跑什么 |
|---|---|---|---|
| EL0 | 用户态 | 只能访问自己的虚拟内存，不能碰硬件 | 你的程序 |
| EL1 | 内核态 | 访问全部内存、直接操作硬件 | Linux 内核 |

你的程序跑在 EL0，却要读文件、发网络包、访问另一进程的内存——
这些只有 EL1 才有权做。于是需要一个**受控的入口**，这就是系统调用。

```
用户程序                          内核
  │
  │  syscall(SYS_write, 1, buf, 20)
  │  ──── svc #0 指令 ──────────→  查系统调用表
  │                                sys_write(fd, buf, count)
  │                                检查参数合法性
  │                                真正写设备
  │  ←─── 返回返回值 ────────────  eret 回到用户态
  ↓
继续执行
```

关键：用户程序**不能**直接跳到内核代码，只能通过 `svc`（ARM64）/ `syscall`（x86-64）
指令触发一个异常，让 CPU 自动切换到内核态并跳转到内核指定的入口。

> [!note] 为什么必须这样
> 如果用户程序能随意执行内核代码，那任何程序都能读写整个内存、关掉所有安全检查。
> 系统调用是**唯一的、受控的、可审计的**入口。

## 系统调用号

内核用一张表（syscall table）管理所有系统调用，每个有一个编号。

**不同架构编号不一样**（这是本项目 `SysHal.h` 里那段条件编译的原因）：

| 系统调用 | arm64 | arm(32) | x86_64 | i386 |
|---|---|---|---|---|
| `read` | 63 | 3 | 0 | 3 |
| `write` | 64 | 4 | 1 | 4 |
| `openat` | 56 | 322 | 257 | 295 |
| `process_vm_readv` | **270** | 376 | 310 | 347 |
| `process_vm_writev` | **271** | 377 | 311 | 348 |

本项目代码：

```c
#if defined(__arm__)
    int process_vm_readv_syscall  = 376;
    int process_vm_writev_syscall = 377;
#elif defined(__aarch64__)
    int process_vm_readv_syscall  = 270;      // ← Android 手机
    int process_vm_writev_syscall = 271;
#elif defined(__i386__)
    int process_vm_readv_syscall  = 347;
    int process_vm_writev_syscall = 348;
#else
    int process_vm_readv_syscall  = 310;      // x86_64
    int process_vm_writev_syscall = 311;
#endif
```

> [!tip] 一般不用自己写编号
> `<sys/syscall.h>` 里定义了 `SYS_write`、`__NR_process_vm_readv` 等宏。
> 本项目手写编号的原因：`process_vm_readv` 在部分老 NDK 的头文件里没有定义，
> 手写编号 + `syscall()` 是最稳的兜底方案。

## syscall() 函数

```c
#include <unistd.h>
#include <sys/syscall.h>

long syscall(long number, ...);
```

最多 6 个参数（对应 6 个寄存器）。返回值：
- `>= 0`：成功，含义随调用而定（如 `read` 返回字节数）
- `-1`：失败，具体原因在 `errno` 里

> [!warning] syscall() 不会自动设置 errno
> glibc 的 `syscall()` 封装会设置，但直接内联汇编不会。
> 保守做法：
> ```c
> long ret = syscall(NR, ...);
> if (ret < 0) { errno = -ret; perror("failed"); }
> ```

## glibc 包装 vs 直接 syscall

| 方式 | 优点 | 缺点 |
|---|---|---|
| `open()` / `read()` | 类型安全、自动设 errno、有缓存 | 需要头文件里有 |
| `syscall(SYS_openat, ...)` | 不依赖头文件、可用新调用 | 手写易错、无类型检查 |

本项目两种都在用：
- 常规文件操作用 libc 的 `fopen`/`fgets`（第 22 章）
- `process_vm_readv` 用裸 `syscall`（因为 NDK 头文件不一定有）

## 自己实现一次 syscall 包装

> [!note] 下面出现的 `struct iovec` 是什么
> `iovec`（I/O vector，IO 向量）是"**一段内存的描述**"——记录"从哪个地址开始、多长"：
> ```c
> struct iovec {
>     void  *iov_base;   // 起始地址
>     size_t iov_len;    // 长度
> };
> ```
> `process_vm_readv` 用它描述"从对方进程读哪段、存到我这边哪段"。**第 74 章会完整讲跨进程读取，这里先看个形状。**

```c
#include <unistd.h>
#include <sys/syscall.h>
#include <sys/uio.h>
#include <errno.h>
#include <stdio.h>
#include <string.h>

// 手写 process_vm_readv
ssize_t my_process_vm_readv(pid_t pid,
                            const struct iovec *local_iov, unsigned long liovcnt,
                            const struct iovec *remote_iov, unsigned long riovcnt,
                            unsigned long flags) {
#ifdef __aarch64__
    const long nr = 270;
#else
    const long nr = 310;   // x86_64
#endif
    return syscall(nr, pid, local_iov, liovcnt, remote_iov, riovcnt, flags);
}
```

第 74 章会把这段扩展成完整的跨进程读取器。

> [!note] `strace` 是什么
> `strace` 是 Linux 的"**系统调用跟踪器**"——运行程序时，把它调用的每一个系统调用、参数、返回值都打印出来。
> ```bash
> strace ./app        # 运行并打印所有系统调用
> ```
> 它是排查"程序为什么打不开文件""为什么卡住"的利器。**Android 上需要 root 且有 strace 才能用。**

## strace：看程序到底调用了什么

```bash
strace ./hello
```

输出：

```
execve("./hello", ["./hello"], 0x7ffd...) = 0
write(1, "Hello from syscall\n", 19)    = 19
exit_group(0)                           = ?
```

每一个系统调用、参数、返回值都列出来了。排错神器：

```bash
strace -e trace=file ./app       # 只看文件相关
strace -e trace=memory ./app     # 只看内存相关
strace -f ./app                  # 跟踪子线程
strace -p 1234                   # 附加到正在运行的进程
```

Android 上：`adb shell strace -p <pid>`（需要 root 且设备有 strace）。

> [!tip] 用 strace 解释"为什么打不开文件"
> ```bash
> strace -e trace=file ./app 2>&1 | grep Config
> # openat(AT_FDCWD, "/data/Config", O_RDONLY) = -1 EACCES (Permission denied)
> ```
> 一眼看出是权限问题（`EACCES`），不用猜。

## 系统调用的开销

一次 `syscall` 涉及：
1. 保存用户态寄存器
2. 切换 CPU 特权级
3. 内核查表、检查参数
4. 执行
5. 恢复寄存器、切换回用户态

大约 **几百纳秒到几微秒**。看起来很快，但：

> [!warning] 本项目每帧要读几千次
> 假设每帧读 200 个对象 × 10 次 = 2000 次 syscall × 2µs = **4ms**。
> 60fps 一帧只有 16.6ms，光读内存就占掉 1/4。
> 这就是为什么第 81 章要专门讲"批量读与缓存"——把 2000 次压到几十次。

## 内核态是怎么访问用户内存的

内核不能直接解引用用户传进来的指针（可能是恶意地址）。
它用专用函数：

```c
copy_from_user(kernel_buf, user_ptr, len);   // 内核读用户内存
copy_to_user(user_ptr, kernel_buf, len);     // 内核写用户内存
```

这两个函数内部会检查地址是否合法，非法就返回错误而不是崩溃。

`process_vm_readv` 更进一步——它允许**指定另一个进程**，
内核拿着那个进程的页表去翻译远程地址。这是内核才能做的事。

## 动手：用 syscall 写文件

> [!tip] Windows 用户怎么办
> 本练习用了 `syscall(SYS_openat, ...)` 和 `strace`，都是 Linux 接口。**Windows 上建议用 WSL**；`strace` 在 WSL 里可用。

```c
#include <unistd.h>
#include <sys/syscall.h>
#include <fcntl.h>
#include <stdio.h>

int main(void) {
    // openat(AT_FDCWD, path, flags, mode)
    int fd = syscall(SYS_openat, -100, "/tmp/syscall_test.txt",
                     O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("openat"); return 1; }
    printf("fd = %d\n", fd);

    const char *data = "written by raw syscall\n";
    long n = syscall(SYS_write, fd, data, 23);
    printf("wrote %ld bytes\n", n);

    syscall(SYS_close, fd);
    return 0;
}
```

`AT_FDCWD` 的值是 `-100`（定义在 `<fcntl.h>`）。
跑完后 `cat /tmp/syscall_test.txt` 验证。

再用 `strace` 跑一遍，确认系统调用号是什么。
