# 第 28 章 · 静态库与链接顺序

> [!abstract] 本章目标
> 会制作和使用 `.a` 静态库，理解它"按需抽取"的机制和链接顺序陷阱。
> 本项目链接 6 个 Embree 静态库，本章是第 43 章的直接前置。

## 先看 .a 是什么

**静态库 = 一堆 `.o` 打包成的归档文件（archive）**。
本质和 `.zip` 差不多，只不过里面是目标文件。

```bash
ar rcs libmath.a add.o sub.o mul.o       # 打包
ar t libmath.a                            # 列出成员
# add.o
# sub.o
# mul.o

ar x libmath.a add.o                      # 解出某个成员
```

> [!note] `ar` 是什么
> `ar` = **archiver（归档器）**，用来把多个 `.o` 打包成一个 `.a`（静态库）。
> 常用形式：
> ```bash
> ar rcs libxxx.a a.o b.o c.o    # r=替换/添加  c=创建  s=写索引
> ar t libxxx.a                  # 列出成员（table）
> ar x libxxx.a a.o              # 解出某个成员（extract）
> ```
> **`ar` 只打包，不做链接。** 链接发生在你 `gcc main.o libxxx.a` 的时候。

## 制作一个静态库

```bash
# 1. 写源码
cat > mymath.c << 'EOF'
int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }
EOF

cat > mymath.h << 'EOF'
#pragma once
int add(int a, int b);
int sub(int a, int b);
EOF

# 2. 编译成 .o
gcc -c mymath.c -o mymath.o

# 3. 打包
ar rcs libmymath.a mymath.o

# 4. 使用
cat > main.c << 'EOF'
#include <stdio.h>
#include "mymath.h"
int main(void) {
    printf("%d %d\n", add(3, 4), sub(10, 3));
    return 0;
}
EOF
gcc main.c -L. -lmymath -o app
./app          # 7 7
```

`ar` 参数：

| 参数 | 含义 |
|---|---|
| `r` | 替换/插入成员 |
| `c` | 不存在就创建 |
| `s` | 建立索引（**必须有**，否则链接慢或失败） |

`-L.` 指定库的搜索路径，`-lmymath` 表示找 `libmymath.a`。

## 静态库的"按需抽取"机制

链接静态库时，链接器**不会**把整个库都塞进产物。
它只抽取"当前未解决符号需要的那些 `.o`"。

```
main.o 需要 add
   ↓
libmymath.a 里找：哪个 .o 定义了 add？
   ↓
找到了 mymath.o（它同时也有 sub，一并进来）
   ↓
只把 mymath.o 加进产物
```

**关键推论：一个 `.o` 是一个整体单位。**
只要它的任何一个符号被需要，整个 `.o` 都被链接进来（包括你没用到的函数）。

> [!tip] 为什么要把函数拆成多个小 .o
> 如果 `libmymath.a` 里 `add` 和 `sub` 在两个不同的 `.o`，
> 只用 `add` 时，`sub` 就不会被链接进来 → 产物更小。
> 这就是为什么很多库一个源文件只放一个函数。
>
> 本项目 `Android.mk` 里 ImGui 是逐个 `.cpp` 列出的，也是这个道理——
> 配合 `-ffunction-sections -Wl,--gc-sections` 能做到函数级裁剪（第 41 章）。

## 链接顺序陷阱（最容易踩的坑）

```
gcc main.c -L. -lmymath -o app      ✓  库在后面
gcc -L. -lmymath main.c -o app      ✗  库在前面
```

为什么？回顾第 27 章：

> 链接器从左到右扫描，维护"未解决符号"集合。
> 库提供定义，只能解决**已经出现在集合里**的符号。

库放前面时：扫描 `libmymath.a` 时集合还是空的（还没看到 `main.c`），
所以什么都不会被抽取。等看到 `main.c` 需要 `add` 时，库已经过去了。

```
错误顺序：
  libmymath.a（集合空 → 什么都不抽） → main.o（需要 add → 无人解决）✗

正确顺序：
  main.o（需要 add → 加入集合）→ libmymath.a（解决 add）✓
```

**规则：目标文件在前，库在后。**

## 库之间的相互依赖

如果 `libA.a` 用到了 `libB.a` 里的函数：

```
gcc main.o -lA -lB -o app      ✓  A 在 B 前
gcc main.o -lB -lA -o app      ✗  A 需要 B，但 B 已经过去了
```

规则：**被依赖的库放右边。**

循环依赖（`A` 用 `B`，`B` 也用 `A`）：

```bash
gcc main.o -lA -lB -lA -o app                        # 重复列
gcc main.o -Wl,--start-group -lA -lB -Wl,--end-group -o app   # 分组反复扫
```

## 本项目的 6 个 Embree 静态库

```makefile
LOCAL_STATIC_LIBRARIES := \
    embree_prebuilt \
    lexers_prebuilt \
    math_prebuilt \
    sys_prebuilt \
    task_prebuilt \
    simd_prebuilt
```

每个库的职责：

| 库 | 内容 |
|---|---|
| `libembree4.a` | 核心：BVH 构建、光线遍历、几何管理 |
| `liblexers.a` | 解析（如 `.obj` 加载器的词法分析） |
| `libmath.a` | 数学工具（向量、包围盒、随机数） |
| `libsimd.a` | SIMD 抽象层（SSE/AVX/NEON 统一接口） |
| `libsys.a` | 系统抽象（线程、文件、内存分配） |
| `libtasking.a` | 任务调度（多线程并行构建 BVH） |

依赖方向大致是：

```
embree4 → tasking → sys → math → simd
              ↑
           lexers
```

所以正确顺序应该是"高层在前、底层在后"。
本项目 `LOCAL_STATIC_LIBRARIES` 里 `simd_prebuilt` 放最后，正好符合。

> [!danger] 遇到满屏 undefined reference 怎么办
> 如果链接 Embree 时报一堆 `undefined reference to rtcXXX`：
> 1. 先确认顺序（被依赖的放后面）
> 2. 加大 `-Wl,--start-group ... --end-group`
> 3. 用 `nm -g libembree4.a | grep U` 看它还需要什么，逐个补库

## 查看静态库内容

```bash
# 列出成员
ar t libembree4.a | head

# 列出成员里定义的符号
nm -g libembree4.a | grep ' T ' | head

# 找出某个符号在哪个 .o 里
nm -A libembree4.a 2>/dev/null | grep ' T rtcNewDevice'
# libembree4.a:device.o:0000000000001234 T rtcNewDevice

# 查看未定义符号（需要别的库提供）
nm -g --undefined-only libembree4.a | sort -u | head -20
```

最后一条用来诊断"这个库还依赖什么"。

## 静态库 vs 动态库选型

| 场景 | 选静态 | 选动态 |
|---|---|---|
| 只有一个程序用 | ✓ | |
| 多个程序共用 | | ✓（省磁盘/内存） |
| 需要独立更新 | | ✓ |
| 减少运行时依赖 | ✓ | |
| 减小主程序体积 | | ✓ |

本项目全用静态（ImGui 源码 + Embree .a），因为：
- 只产出一个可执行文件
- 不希望运行时依赖额外的 `.so`
- 便于分发（单文件）

代价是产物较大（Embree 的 `.a` 加起来几十 MB，链接后抽取的部分也有数 MB）。

## 头文件 + 静态库：分发的最小单位

给别人用你的库，给这两样：

```
include/mylib.h      ← 声明（别人看得到）
lib/libmylib.a       ← 实现（机器码，看不懂源码）
```

这正是 Embree 的分发方式：本项目只有 `rtcore.h` 等头文件和 6 个 `.a`，
**没有 Embree 的源码**。所以你能调用 `rtcNewDevice`，但看不到它怎么实现。

> [!note] 头文件和库必须配套
> 头文件改了（结构体布局变了）但库没重新编译 → 灾难性错误（内存布局不匹配）。
> 第三方库升级时，头文件和 `.a` 一定要同时换。

## 动手：多文件静态库 + 顺序实验

> [!tip] Windows 用户怎么办
> `ar`/`gcc` 在 **Git Bash（w64devkit）里都有**，本练习可在 Windows 上做。

```bash
mkdir -p libtest && cd libtest

# 三个源文件，故意做成依赖链：high → mid → low
cat > low.c << 'EOF'
int low_func(void) { return 1; }
EOF

cat > mid.c << 'EOF'
int low_func(void);
int mid_func(void) { return low_func() + 10; }
EOF

cat > high.c << 'EOF'
int mid_func(void);
int high_func(void) { return mid_func() + 100; }
EOF

cat > app.c << 'EOF'
#include <stdio.h>
int high_func(void);
int main(void) { printf("%d\n", high_func()); return 0; }
EOF

# 分别打包（每个 .o 单独一个库）
gcc -c low.c -o low.o   && ar rcs liblow.a low.o
gcc -c mid.c -o mid.o   && ar rcs libmid.a mid.o
gcc -c high.c -o high.o && ar rcs libhigh.a high.o
```

现在试四种顺序，观察哪些能过：

```bash
gcc app.c -L. -lhigh -lmid -llow -o app     # A：正确顺序
gcc app.c -L. -llow -lmid -lhigh -o app     # B：反序
gcc app.c -L. -lmid -lhigh -llow -o app     # C：乱序
gcc app.c -Wl,--start-group -L. -llow -lmid -lhigh -Wl,--end-group -o app  # D：分组
```

预期：A、D 成功；B、C 报 `undefined reference`。

再用 `nm --undefined-only libmid.a` 确认：mid 需要 `low_func`。
