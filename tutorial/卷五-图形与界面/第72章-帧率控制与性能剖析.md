# 第 72 章 · 帧率控制与性能剖析

> [!abstract] 本章目标
> 掌握稳定的帧率控制和性能测量方法。
> **卷五收官章**，本卷产出的 `overlay` 到这里能稳定跑起来。

> [!note] 承上
> 卷五从"管线"走到"触摸"，overlay 框架已成型。
> 本章收官：**让它稳定跑**——限帧 + 性能剖析。

## 先看为什么要限帧

覆盖层如果无限跑：

```
while (true) { 渲染(); }     // 能跑 500 FPS
```

后果：
- CPU/GPU 满载，手机发热
- 抢占游戏进程的 CPU 时间 → **游戏掉帧**
- 耗电

**限帧的目的是给游戏让出资源。**

## 帧率控制的三种写法

### 写法一：sleep 固定时长（不准）

```cpp
while (running) {
    RenderFrame();
    usleep(16000);      // 16ms，约 60fps
}
```

问题：`RenderFrame()` 本身耗时没算进去，实际帧率低于 60。

```
实际周期 = 渲染耗时 + 16ms
若渲染 5ms → 21ms → 47 FPS（不是 60）
```

### 写法二：sleep_until 绝对时间（准）

本项目 `limit_gui_frame_rate()`：

```cpp
static void limit_gui_frame_rate() {
    static std::chrono::steady_clock::time_point nextFrame{};
    const auto now = std::chrono::steady_clock::now();

    const int targetFps = std::clamp(ConfigManager::Settings.gui_frame_rate, 60, 185);
    const auto framePeriod = std::chrono::duration_cast<
        std::chrono::steady_clock::duration>(
        std::chrono::duration<double>(1.0 / targetFps));

    if (nextFrame == std::chrono::steady_clock::time_point{}) nextFrame = now;
    if (now < nextFrame) std::this_thread::sleep_until(nextFrame);

    const auto frameStart = std::chrono::steady_clock::now();
    nextFrame += framePeriod;                       // ★ 累加，不是重新赋值
    if (nextFrame <= frameStart) nextFrame = frameStart + framePeriod;
}
```

三个要点：

| 要点 | 原因 |
|---|---|
| `nextFrame += framePeriod` | 累积，避免误差累积（用 `= now + period` 会漂移） |
| `if (nextFrame <= frameStart)` | 落后太多时重新对齐（追帧失败就放弃追） |
| `std::clamp(fps, 60, 185)` | 限制范围，防异常值 |

### 写法三：vsync 同步（最准）

Vulkan 用 `VK_PRESENT_MODE_FIFO_KHR`（第 59 章）：
`vkQueuePresentKHR` 会阻塞到下一个垂直同步信号。

**最省电、最平滑**，但帧率被锁定为屏幕刷新率。

本项目两种结合：GUI 帧率滑块（60~185）+ 呈现模式。

## 测量帧率

```cpp
// 简单版：每 N 帧统计
static int frameCount = 0;
static auto lastTime = std::chrono::steady_clock::now();

frameCount++;
auto now = std::chrono::steady_clock::now();
auto elapsed = std::chrono::duration<float>(now - lastTime).count();
if (elapsed >= 1.0f) {
    float fps = frameCount / elapsed;
    printf("FPS: %.1f\n", fps);
    frameCount = 0;
    lastTime = now;
}
```

ImGui 自带：

```cpp
ImGui::Text("平均 %.3f ms/frame (%.1f FPS)",
            1000.0f / ImGui::GetIO().Framerate,
            ImGui::GetIO().Framerate);
```

本项目"信息"标签页就用了这个（真实代码）：

```cpp
ImGui::TextColored(ImVec4(1.0f, 0.0f, 1.0f, 1.0f),
                   "应用平均 %.3f ms/frame (%.1f FPS)",
                   1000.0f / ImGui::GetIO().Framerate,
                   ImGui::GetIO().Framerate);
```

## 分段计时：找出瓶颈

光看总帧时不够，要分段：

```cpp
struct ProfileScope {
    const char *name;
    std::chrono::steady_clock::time_point start;

    ProfileScope(const char *n) : name(n), start(std::chrono::steady_clock::now()) {}
    ~ProfileScope() {
        auto end = std::chrono::steady_clock::now();
        float ms = std::chrono::duration<float, std::milli>(end - start).count();
        g_profileTimes[name] += ms;
    }
};

// 用法
void Frame() {
    { ProfileScope s("ReadMemory");   UpdateGameData(); }
    { ProfileScope s("ESP");          DrawPlayer(draw); }
    { ProfileScope s("PhysX");        DrawESP(draw); }
    { ProfileScope s("Render");       graphics->EndFrame(); }
}
```

跑一帧后打印各段耗时：

```
ReadMemory: 4.2 ms   ← 瓶颈在这！
ESP:        0.8 ms
PhysX:      1.1 ms
Render:     2.3 ms
-------------------
总计:       8.4 ms
```

**本项目真正的瓶颈几乎总是在 ReadMemory**（第 81 章解决）。

## 常见瓶颈与对策

| 瓶颈 | 症状 | 对策 |
|---|---|---|
| 内存读取 | 每帧数千次 I/O | 批量读、缓存（第 81 章） |
| 骨骼计算 | 目标多时变慢 | 降采样、距离剔除 |
| 遮挡射线 | 开 PhysX 后变慢 | 只对准星射线做、降频 |
| 绘制 | 顶点数多 | 减少绘制项 |
| 触摸读取 | `dumpsys` 之类 | 节流（第 68 章） |

## 用 simpleperf 剖析（Android）

NDK 自带的性能剖析工具：

```bash
# 采样 10 秒
adb shell simpleperf record -p <pid> -o /data/local/tmp/perf.data --duration 10
adb pull /data/local/tmp/perf.data
simpleperf report -i perf.data
```

输出类似：

```
Overhead  Command  Symbol
  45.23%   klbq     MemDriver::Read
  18.11%   klbq     GetBoneWorldPos
  10.02%   klbq     libc.so (memcpy)
  ...
```

**直接指出哪个函数最耗时。**

## 用 systrace / Perfetto

更宏观的视角（看系统调用、CPU 调度）：

```bash
# 抓 5 秒
adb shell perfetto -o /data/misc/perfetto-traces/trace -t 5s \
    sched freq idle am wm gfx view
adb pull /data/misc/perfetto-traces/trace
```

用 `https://ui.perfetto.dev` 打开，能看到：
- 每个线程在干什么
- CPU 频率变化
- 帧的耗时分布

## 内存占用

```bash
adb shell dumpsys meminfo <pid>
```

关注：

| 指标 | 含义 |
|---|---|
| `PSS Total` | PSS（Proportional Set Size，按比例分摊的物理内存）总量 |
| `Private Dirty` | 独占的脏页 |
| `.so mmap` | 动态库映射 |
| `.oat mmap` | （Java 才有） |

本项目因为内嵌了几 MB 字体 + 静态链接 Embree + libc++，
PSS 通常在 30~80 MB。

## 发热与降频

持续高负载会触发温控降频：

```bash
# 看 CPU 频率
adb shell cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq

# 看温度
adb shell cat /sys/class/thermal/thermal_zone0/temp
```

对策：
- 限帧（60fps 而非 120）
- 减少每帧工作量
- 后台线程降频（本项目的 PhysX 更新线程是 2s/3s/300ms）

## 本项目的性能相关设计

| 设计 | 作用 |
|---|---|
| GUI 帧率滑块 (60-185) | 用户可调，平衡流畅与占用 |
| `screen_config()` 250ms 节流 | 避免频繁 `dumpsys` |
| PhysX 三线程 2s/3s/300ms | 后台低频更新，不阻塞渲染 |
| `limit_gui_frame_rate()` 累积对齐 | 稳定帧率 |
| 信息页实时显示 FPS | 便于用户自查 |

## 动手：给 overlay 加性能面板

> [!important] 前置条件
> 需要 **Android 设备**（`atrace`/性能面板都要在设备上观察）。

```cpp
struct PerfMonitor {
    float frameTimes[120] = {};      // 最近 120 帧
    int   index = 0;
    float readMs = 0, drawMs = 0, renderMs = 0;

    void PushFrame(float total) {
        frameTimes[index] = total;
        index = (index + 1) % 120;
    }

    void DrawUI() {
        float avg = 0, max = 0;
        for (float t : frameTimes) { avg += t; max = std::max(max, t); }
        avg /= 120;

        ImGui::Begin("性能");
        ImGui::Text("平均帧时: %.2f ms (%.1f FPS)", avg, 1000.0f/avg);
        ImGui::Text("最差帧时: %.2f ms", max);
        ImGui::Text("内存读取: %.2f ms", readMs);
        ImGui::Text("ESP 绘制: %.2f ms", drawMs);
        ImGui::Text("Vulkan  : %.2f ms", renderMs);

        // 帧时曲线
        ImGui::PlotLines("帧时", frameTimes, 120, index,
                         nullptr, 0.0f, 33.0f, ImVec2(0, 60));

        // 60fps 基准线（16.6ms）
        if (avg > 16.6f)
            ImGui::TextColored(ImVec4(1,0,0,1), "超过 60fps 预算！");
        ImGui::End();
    }
};
```

用 `ImGui::PlotLines` 画一条帧时曲线——**肉眼就能看出是否稳定**。

## 动手验证清单

- [ ] **加帧率显示**：`ImGui::GetIO().Framerate` → 屏幕上显示 fps
- [ ] **限帧**：用 `vsync` 或 `sleep` 限制 60fps → CPU 占用下降
- [ ] **性能剖析**：用 `perfetto`/`atrace` 抓一段 trace → 看每帧耗时分布
- [ ] **查耗时热点**：`adb shell atrace -t 5 gfx view` → 找出耗时最长的阶段
- [ ] **优化前后对比**：优化一处 → 帧时间下降

> [!tip] 抓 trace 的时机
> 先开性能面板看帧时间，飘红（>16ms）时再用 atrace/perfetto 抓那段。
> 别盲目优化——先定位热点（第 71、72 章）。

## 常见坑排查表

| 症状 | 最可能的原因 | 解法 |
|---|---|---|
| 帧率**上不去** | 没限帧（CPU 空转）| 用 vsync 或 `sleep` 限制 |
| 帧率**忽高忽低** | 每帧开销不均 | `atrace` 抓 trace 找尖峰 |
| CPU 占用**很高但帧率低** | 后台线程忙等 | 检查线程循环有没有 `sleep` |
| 优化后**没变化** | 优化了非热点 | 先用 atrace 定位真正的瓶颈 |
