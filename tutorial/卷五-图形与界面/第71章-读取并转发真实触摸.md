# 第 71 章 · 读取并转发真实触摸

> [!abstract] 本章目标
> 实现"独占读取 + 处理后重新注入"的完整回路，
> 让覆盖层既能接收触摸，又不妨碍游戏操作。

> [!note] 承上
> 上一章学会了注入触摸。
> 本章把"读真实触摸 + 条件转发"拼成完整回路——菜单能点，菜单外能穿透到游戏。

## 先看要解决的问题

覆盖层创建后，它**不吃触摸**（只是个图层），触摸照常传给游戏。
但我们希望：

```
点菜单按钮 → 菜单响应，游戏不响应
点菜单之外 → 游戏响应，菜单不响应
```

这就是"命中测试 + 条件转发"。

## 两种工作模式

| 模式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **透传**（简单） | 不独占，只读一份副本 | 不影响游戏 | 菜单点不到 |
| **独占转发** | EVIOCGRAB + uinput 重注入 | 可拦截 | 有延迟、有风险 |

> [!important] 本项目实际用的是**透传**
> 真实项目 `main.cpp` 里是：
> ```cpp
> Touch::Init({(float)::abs_ScreenX, (float)::abs_ScreenY}, true);   // ★ 第二个参数 = true
> ```
> 第二个参数 `p_readOnly = true`，意味着 TouchHelperA **只读、不独占**（不 `EVIOCGRAB`）。
> 所以触摸会**照常到达游戏**，ImGui 只是"旁听"一份副本。
>
> **本章为什么还讲"独占转发"**：它是 TouchHelperA 支持的另一条路径
> （`Touch::Init(..., false)` 时会 `EVIOCGRAB` + 建 uinput 重注入），
> 用于"菜单要拦截、游戏不响应"的场景。理解它有助于你读懂 `TouchHelperA.cpp` 的全貌，
> 但**默认配置下项目跑的是透传**。

## 独占转发的完整回路

```
真实触摸屏 /dev/input/event2
    │  EVIOCGRAB（独占）
    ↓
我们的程序
    │  1. 解析事件
    │  2. 判断：点在 ImGui 窗口内吗？
    │     ├─ 是 → 只喂给 ImGui，不转发
    │     └─ 否 → 转发给虚拟设备
    ↓
/dev/uinput → 虚拟触摸设备
    ↓
系统 → 游戏
```

## 判断"点在窗口内"

ImGui 提供了接口：

```cpp
// 方法 1：查询是否有窗口被 hover
bool hovered = ImGui::IsWindowHovered(
    ImGuiHoveredFlags_AnyWindow |
    ImGuiHoveredFlags_AllowWhenBlockedByActiveItem);

// 方法 2：查询鼠标位置是否在任意窗口内
bool overUI = ImGui::IsAnyWindowHovered();

// 方法 3：拿到当前窗口的矩形自己判断
ImGuiWindow *win = ImGui::GetCurrentWindow();
ImRect rect = win->Rect();
bool inside = rect.Contains(ImGui::GetMousePos());
```

本项目保存了窗口矩形（`g_window`），可以自己判断：

```cpp
extern ImGuiWindow *g_window;

bool IsTouchOnUI(float x, float y) {
    if (!g_window) return false;
    ImVec2 pos = g_window->Pos;
    ImVec2 size = g_window->Size;
    return x >= pos.x && x <= pos.x + size.x &&
           y >= pos.y && y <= pos.y + size.y;
}
```

## 转发的实现

真实项目里，虚拟设备的 fd 叫 **`nowfd`**（不是 `uinputFd`），
在 `Touch::Init(..., false)` 时创建。转发时把事件写进 `nowfd`：

```cpp
// 说明：nowfd 是 Touch::Init 里 open("/dev/uinput") 拿到的 fd
//       （第 70 章讲 uinput 时已讲过怎么创建虚拟触摸设备）
void Touch::Upload() {
    for (auto &dev : devices) {
        for (int i = 0; i < 10; i++) {
            auto &f = dev.Finger[i];
            if (!f.isDown) continue;

            // 判断是否要转发
            if (IsTouchOnUI(f.pos.x, f.pos.y)) {
                // 点在 UI 上：不转发，只更新 ImGui
                continue;
            }

            // 转发到虚拟设备（写 nowfd）
            EmitEvent(nowfd, EV_ABS, ABS_MT_SLOT, i);
            EmitEvent(nowfd, EV_ABS, ABS_MT_TRACKING_ID, f.id);
            int tx = (int)(f.pos.x * dev.S2TX);
            int ty = (int)(f.pos.y * dev.S2TY);
            EmitEvent(nowfd, EV_ABS, ABS_MT_POSITION_X, tx);
            EmitEvent(nowfd, EV_ABS, ABS_MT_POSITION_Y, ty);
        }
        EmitEvent(nowfd, EV_SYN, SYN_REPORT, 0);
    }
}
```

> [!note] `EmitEvent` 是本章的简化写法
> 真实项目 `TouchHelperA.cpp` 的 `Upload()` 不逐个 `write`，
> 而是先填满一个 `input.event[]` 数组，最后**一次性 `write(nowfd, ...)`**（更高效）。
> 这里的 `EmitEvent` 帮你理解"每条事件最终都写进 nowfd"，结构等价。

## 为什么需要"复制"而不是"直接放行"

你可能会想：不独占不就行了？

问题在于：**如果菜单要响应点击，必须知道触摸；
如果游戏不该响应，必须阻止事件到达游戏。**
这两个需求同时满足，只能"拦截 + 有条件重发"。

## 延迟问题

转发链路每多一环就多一点延迟：

```
真实触摸:  硬件 → 内核 → InputReader → App        ≈ 10ms
转发:      硬件 → 内核 → 我们(用户态) → uinput → 内核 → InputReader → App   ≈ 15-25ms
```

多了约 10ms。对大多数操作无感，对音游/格斗游戏可能觉察。

**优化手段**：
- 减少每帧处理时间（不要在处理触摸时做重活）
- 用 `O_NONBLOCK` + `poll` 及时读取
- 事件批处理（攒几个一起发）

## 独占的风险与恢复

```cpp
// 独占
ioctl(fd, EVIOCGRAB, 1);

// 必须释放（正常退出、异常、崩溃都要）
ioctl(fd, EVIOCGRAB, 0);
```

**如果程序崩溃没释放**：手机触摸完全失效。

应急方案：

```bash
# 用 adb 模拟按键还能操作
adb shell input keyevent KEYCODE_BACK
adb shell input tap 500 1000

# 重启 Android 框架（不丢数据）
adb shell stop && adb shell start

# 实在不行重启
adb reboot
```

> [!danger] 开发时务必留后路
> - 加一个"看门狗"：一段时间没心跳就自动释放
> - 或者提供快捷退出键（音量键组合）
> - 或者干脆不独占，用"透明转发"模式

## 更安全的替代：只在需要时 GRAB

```cpp
// 菜单可见且用户正在与菜单交互时才独占
bool shouldGrab = ImGui::IsAnyWindowHovered() || ImGui::IsAnyItemActive();

if (shouldGrab && !grabbed) {
    ioctl(fd, EVIOCGRAB, 1);
    grabbed = true;
} else if (!shouldGrab && grabbed) {
    ioctl(fd, EVIOCGRAB, 0);
    grabbed = false;
}
```

这样大部分时间不独占，风险大大降低。

## 本项目的初始化流程

```cpp
// main.cpp
Touch::Init({(float)abs_ScreenX, (float)abs_ScreenY}, true);
Touch::setOrientation(displayInfo.orientation);
```

`Init` 的第二个参数 `p_readOnly`：

```cpp
bool Touch::Init(const My_Vector2 &s, bool p_readOnly) {
    // p_readOnly = true  → 只 O_RDONLY，不独占
    // p_readOnly = false → O_RDWR，可以 GRAB
}
```

本项目传的是 `true`（只读模式）。结合 `TouchHelperA.cpp` 的源码可以确认：
**`readOnly = true` 时，它既不 `EVIOCGRAB`（不独占），也不打开 `/dev/uinput`（不注入）**——
它只是被动读一份触摸副本，喂给 ImGui 做交互。游戏照常收到触摸。

> [!note] 项目的触摸分工（对照源码）
> | 用途 | 走哪条路 | 是否注入 |
> |---|---|---|
> | ImGui 菜单交互 | `TouchHelperA`（默认只读） | 否（只旁听） |
> | 自瞄点屏幕 | 内核驱动 `Driver::TouchDown/Move/Up` | 是（内核层） |
>
> 也就是说：**默认配置下，`TouchHelperA` 不注入触摸**；
> 它注入（写 `nowfd`）的前提是 `Touch::Init(..., false)`。
> 自瞄的注入走的是另一条路（内核驱动，卷六/卷八讲），更低延迟、更难检测。

## 触摸缩放：两套变量，方向相反

物理触摸屏分辨率 ≠ 屏幕分辨率（触摸轴量程可能是 32767，而屏幕只有 1080）。
本项目里有**两个**缩放量，方向相反，别搞混：

| 变量 | 计算 | 用途 |
|---|---|---|
| `device.S2TX/S2TY` | `screenW / absX.maximum` | **触摸值 → 屏幕坐标**：`screenX = touchValue * S2TX` |
| `touch_scale.x/y` | `touchAxisMax.x / screenW` | **屏幕坐标 → 触摸值**：`touchValue = screenX * touch_scale.x` |

```cpp
// 每个设备：S2TX = 屏幕/触摸量程（把读到的触摸值乘成屏幕坐标）
struct input_absinfo absX;
ioctl(fd, EVIOCGABS(ABS_MT_POSITION_X), &absX);
device.S2TX = (float)screenW / (float)absX.maximum;   // 触摸 → 屏幕

// 读线程里：把原始触摸值换算成屏幕坐标
device.Finger[latest].pos.x = (float)ie.value * device.S2TX;
```

**注入**（把 ImGui 的屏幕坐标发成触摸值）时用另一个方向：

```cpp
// 屏幕坐标 → 触摸值（先乘 touch_scale，写进 uinput）
touch.pos = My_Vector2(x, y) * touch_scale;   // touch_scale = touchMax / screen

// 反向：触摸值 → 屏幕坐标（读路径用）
My_Vector2 Touch::Touch2Screen(const My_Vector2 &coord) {
    return {coord.x / touch_scale.x, coord.y / touch_scale.y};
}
```

> [!warning] 别把 S2TX 和 touch_scale 当成一回事
> 两者互为倒数：`S2TX ≈ 1 / touch_scale`。
> **读触摸**（触摸值 → 屏幕）用 `× S2TX`；**注入触摸**（屏幕 → 触摸值）用 `× touch_scale`。
> 用反了，坐标会差几十倍（32767/1080 ≈ 30 倍）。

## 动手：带命中测试的转发器

在上一章的虚拟点击器基础上，加一个"禁区"：

```cpp
// 屏幕左上角 400x300 是"UI 区"，点在这里不转发
bool IsInUIZone(int x, int y) {
    return x >= 0 && x <= 400 && y >= 0 && y <= 300;
}

void OnTouch(int slot, int x, int y, bool down) {
    if (IsInUIZone(x, y)) {
        printf("[UI区] 拦截: (%d,%d) %s\n", x, y, down ? "按下" : "抬起");
        // 不转发，只自己处理
        return;
    }
    printf("[转发] (%d,%d) %s\n", x, y, down ? "按下" : "抬起");
    if (down) TouchDown(nowfd, slot, x, y);
    else      TouchUp(nowfd, slot);
}
```

开启"指针位置"显示，测试：
1. 点 UI 区 → 指针位置不更新（被拦截）
2. 点 UI 区外 → 指针位置跟着动（已转发）

## 常见问题

| 现象 | 原因 | 解法 |
|---|---|---|
| 菜单点不到 | 没独占，事件直接给了游戏 | 开 GRAB |
| 游戏点不到 | 一直独占且没转发 | 检查转发逻辑 |
| 触摸延迟明显 | 每帧处理太慢 | 优化循环、减少 I/O |
| 崩溃后触摸失灵 | 没 UNGRAB | 加信号处理 / 看门狗 |
| 多点触控乱跳 | slot 管理错误 | 每个手指独立 slot + tracking id |
| 坐标偏移 | S2TX/S2TY 没算 | 用 `EVIOCGABS` 查真实范围 |
