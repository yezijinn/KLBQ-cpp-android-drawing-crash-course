# 第 03 章 · 从源码到可执行文件

> [!abstract] 本章目标
> 拆开"编译"这个黑盒子，看清四个阶段各做了什么。
> 你会亲手产生 `.i` `.s` `.o` 四种中间文件，并知道去看哪一个。

## 先看四个中间产物

对同一个 `hello.c` 分别跑四条命令，会依次产生四个文件：

```bash
gcc -E hello.c -o hello.i     # 预处理 → 一坨展开后的 C 代码
gcc -S hello.i -o hello.s     # 编译   → 汇汇编指令
gcc -c hello.s -o hello.o     # 汇编   → 二进制机器码（还不能跑）
gcc    hello.o -o hello.exe   # 链接   → 可执行程序
```

| 文件 | 内容 | 大小 | 人能读懂吗 |
|---|---|---|---|
| `hello.c` | 你的源码 | ~100 字节 | 能 |
| `hello.i` | 展开所有 `#include` 后的源码 | ~20 KB | 勉强 |
| `hello.s` | 汇编指令 | ~2 KB | 学完第 25 章能 |
| `hello.o` | 机器码 + 符号表 | ~1 KB | 靠工具（第 30 章） |
| `hello.exe` | 完整可执行 | ~50 KB | 靠工具 |

打开 `hello.i` 你会震惊：你写了 5 行，它变成了 800 行——因为 `stdio.h` 被整个粘了进来。

## 四个阶段各干了什么

```
hello.c ──[预处理器]──> hello.i ──[编译器]──> hello.s ──[汇编器]──> hello.o ──[链接器]──> hello.exe
           处理 #           翻译成汇编        汇编→机器码       合并 .o 与库
```

### 1. 预处理（Preprocessing）

处理所有以 `#` 开头的行：

- `#include <xxx.h>` → 把文件内容贴进来
- `#define A B` → 文本替换
- `#ifdef / #endif` → 决定哪些代码留下

产物还是 C 代码，只是变肥了。（第 10 章详解）

### 2. 编译（Compilation）

把 C 代码翻译成汇编。这一步做语法检查、类型检查、优化。
你平时看到的 `error: expected ';' before ...` 就是这一步报的。

### 3. 汇编（Assembly）

把汇编指令逐条翻译成机器码，生成 `.o`（目标文件）。
`.o` 里已经有二进制指令了，但还跑不起来——因为 `printf` 的地址还不知道。

### 4. 链接（Linking）

做两件事：
1. **符号解析**：找到 `printf` 到底在哪（在 `libc` 里）
2. **重定位**：把调用 `printf` 的地址填进去

这就是"未定义引用"错误的来源：

```bash
# 故意写错：把 printf 写成 printff
gcc hello.c -o hello.exe
# undefined reference to `printff'
```

> [!note] `undefined reference` 是链接错误，不是编译错误
> 编译阶段只检查"你声明了没有"，链接阶段才检查"这东西真的存在吗"。
> 以后看到 `undefined reference to xxx`，第一反应是：忘了链接某个库。
> 本项目链接 6 个 Embree 静态库，漏一个就报这种错（第 43 章）。

## 多文件编译

真实工程不可能只有一个文件。假设有：

```c
// math_utils.c
int add(int a, int b) { return a + b; }
```

```c
// main.c
#include <stdio.h>
int add(int a, int b);          // 声明：告诉编译器有这个函数

int main(void) {
    printf("%d\n", add(3, 4));
    return 0;
}
```

编译：

```bash
gcc -c math_utils.c -o math_utils.o
gcc -c main.c -o main.o
gcc main.o math_utils.o -o app.exe
./app.exe    # 输出 7
```

为什么能跑？因为链接器在 `math_utils.o` 里找到了 `add` 的符号，把 `main.o` 里的调用点地址填上了。

> [!danger] 链接顺序有讲究
> ```bash
> gcc math_utils.o main.o -o app.exe   # 可能失败
> gcc main.o math_utils.o -o app.exe   # 正确
> ```
> 传统链接器从左到右扫描：先看到"我需要 add"，再在右边的文件里找。
> 依赖方放左边，被依赖方放右边。第 28 章会详细讲。

## 用 -save-temps 一次看全部

```bash
gcc -save-temps hello.c -o hello.exe
```

当前目录会同时出现 `hello.i`、`hello.s`、`hello.o`、`hello.exe`。
调试构建问题时这个参数很好用。

## make：不用每次手敲四条命令

文件多了以后，手写命令会疯。建一个 `Makefile`：

```makefile
app.exe: main.o math_utils.o
	gcc main.o math_utils.o -o app.exe

main.o: main.c
	gcc -c main.c -o main.o

math_utils.o: math_utils.c
	gcc -c math_utils.c -o math_utils.o
```

然后敲 `make` 就行。

> [!danger] Makefile 的缩进必须是 Tab
> 命令行前面**必须是 Tab 字符**，用空格会报 `missing separator`。
> 这是 Makefile 最经典的坑，没有之一。第 29 章会再讲一次。

`make` 的另一个好处：只重新编译改动过的文件。改了 `main.c`，它不会去重新编译 `math_utils.c`。
