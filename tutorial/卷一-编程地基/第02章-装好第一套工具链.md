# 第 02 章 · 装好第一套工具链

> [!abstract] 本章目标
> 装好能编译 C 程序的环境，并跑通 `hello.c`。
> 本章结束你会得到一个能反复使用的编译命令。

> [!warning] 完全零基础先看这个
> 本章会提到"命令行""PATH 环境变量""路径不能有空格"。
> 如果这些词你还不熟，**先读 [[附录R-绝对零基础前置知识]]**，
> 它从"什么是文件""什么是命令行"开始讲起，不需要任何基础。

> [!important] 先确认一件事：本章命令在**哪个终端**里敲
> Windows 上有**三个命令行工具**——**cmd / PowerShell / Git Bash**——命令**互不通用**。
> 本教程默认用 **Git Bash**（本章第三步会装）。从本章起，每个代码块都标出该在哪个终端敲：
>
> | 代码块的语言标记 | 在哪个终端敲 |
> |---|---|
> | `bash` | **Git Bash**（本教程默认）|
> | `powershell` | **PowerShell** |
> | `bat` | **cmd（命令提示符）** |
> | `text` 或无标记 | 示意图或**程序输出**，不是让你敲的 |
>
> **怎么知道自己在哪个终端**：看提示符——开头有 `PS` 是 PowerShell，
> 只有 `C:\...>` 是 cmd，有 `MINGW64` 和 `~` 是 Git Bash。
>
> 三个终端的完整对照表（含"同一动作三种写法"）见
> [[附录R-绝对零基础前置知识]] 第 3.2 节。
>
> **本章最容易卡的坑**：在 PowerShell 里敲 `where gcc` 会**什么都不输出**，
> 于是误以为 PATH 没配好。真正原因是 `where` 属于 cmd，不是 PowerShell 的命令——
> 第二步会详细讲。

## 方案选择：Windows 上三条路

| 方案 | 安装难度 | 推荐度 | 说明 |
|---|---|---|---|
| **w64devkit** | 极低 | ★★★★★ | 解压即用，自带 gcc/make/gdb，本教程推荐 |
| MSYS2 | 中 | ★★★★ | 包管理器强，后续要装库时方便 |
| Visual Studio | 高 | ★★ | 体积大，但调试器最强 |

本教程用 **w64devkit**，因为它是一个 200MB 的压缩包，解压就能用，不写注册表，删掉就没了。
（另外两条路不走，但流程完全一样：便携包装到 `C:\dev`，`.exe` 安装包装到默认路径。）

## 先定规矩：东西放哪里

装任何工具之前，先决定"它放在哪"。本教程**只用三种位置**，照抄就行：

| 软件的分发形式 | 放哪里 | 为什么这么定 |
|---|---|---|
| **便携包**（`.zip` / `.7z` 压缩包，解压即用） | `C:\dev\<软件名>` | 没有安装器，位置由你定；统一放 `C:\dev` 便于一次性配好 PATH |
| **`.exe` 安装包**（有"下一步 → 下一步 → 完成"向导） | **用默认安装路径，不要改** | 见下面的说明 |
| **你自己写的代码** | `C:\code\<项目名>` | 与工具分开，将来删工具不会连带删掉代码 |

> [!important] `.exe` 安装包为什么"不改路径"
> 网上很多教程会让你把安装路径改到别处。**本教程明确要求：一路"下一步"，用默认路径。** 三个原因：
>
> 1. **安装器会把路径写进注册表和快捷方式**。你改了路径，但注册表、开始菜单、文件关联里记的可能不是同一处；将来卸载、升级、装插件时，工具会去错的地方找东西。
> 2. **改路径本身就是出错高发环节**。手输路径容易带进中文、空格、全角字符——正好踩中下面那条铁律。默认路径（几乎都在 `C:\Program Files\...` 或 `C:\Users\<你的用户名>\AppData\...`）完全没有这个风险。
> 3. **本教程后面给的命令都按默认路径写**。你改了，命令就对不上，报错还得自己翻译一遍。
>
> **唯一例外**：C 盘空间确实不够。那就改到别的盘，并把本教程里出现的路径全部替换成你的实际路径。

> [!danger] 铁律：路径里不能有中文和空格
> ```text
> C:\dev\w64devkit        ✓  全英文、无空格
> C:\开发工具\w64devkit     ✗  含中文
> C:\my tools\w64devkit   ✗  含空格
> ```
> 原因在 [[附录R-绝对零基础前置知识]] 里讲透了（编码不一致 + 空格被当作参数分隔符）。
> 违反这条铁律时，报错信息往往莫名奇妙，新手根本看不出问题在哪。

**本教程只会出现这三种目录，先认个脸：**

| 目录 | 含义 | 在哪里出现 |
|---|---|---|
| `C:\dev\` | **工具目录**：所有便携工具解压到这里 | 第 02 章（w64devkit）、第 33 章（NDK）、第 36 章（platform-tools） |
| `C:\code\` | **代码目录**：你自己写的练习工程放这里 | 第 02 章起 |
| `C:\Program Files\` 等 | **系统默认安装位置**：`.exe` 安装包装出来的 | 第 02 章（VS Code） |

## 第一步：装 w64devkit（便携包 → `C:\dev`）

w64devkit 是**便携包**，所以按上表放到 `C:\dev\w64devkit`：

1. 打开 `https://github.com/skeeto/w64devkit/releases`
2. 下载最新的 `w64devkit-x.x.x.zip`（约 200MB）
3. 解压到 `C:\dev\w64devkit`（**不要放在含中文或空格的路径**）
4. 进入 `C:\dev\w64devkit\bin`，确认里面有 `gcc.exe`、`make.exe`、`gdb.exe`

> [!tip] 为什么解压到 `C:\dev\` 而不是别处
> - 后面第 33 章的 NDK、第 36 章的 platform-tools 也会放进 `C:\dev\`，
>   所有工具集中在一个目录下，出问题时一眼就能看出哪个工具没装对。
> - `C:\dev` 是你自己建的空目录，**不会和系统文件混在一起**，误删也不会影响系统。
> - 目录名短，命令行里少打很多字。

## 第二步：把它加到 PATH

PATH 的作用是：让你在任何目录下敲 `gcc` 都能找到它。

**Windows 11 操作：**
1. 设置 → 系统 → 关于 → 高级系统设置 → 环境变量
2. 上半部分"用户变量"里找到 `Path` → 编辑 → 新建
3. 填入 `C:\dev\w64devkit\bin`
4. 一路确定，然后**重新打开一个终端**（已开的终端不会生效）

> [!danger] 改 PATH 前先备份，改错了能恢复
> PATH 是全局设置，改错会影响所有程序。**操作前**：
> 1. 环境变量窗口 → 用户变量 → 选中 `Path` → **编辑**
> 2. 点 **`编辑文本`** 按钮（不是"新建"）
> 3. **全选 → 复制 → 粘贴到记事本**，存成 `path-backup.txt`
>
> **改错了怎么恢复**：
> - 打开同一窗口，点 `编辑文本`，把 `path-backup.txt` 内容**粘回去**，确定
> - 若已删了关键条目：Windows 默认 PATH 含 `C:\Windows\system32`、`C:\Windows`、
>   `%USERPROFILE%\AppData\Local\Microsoft\WindowsApps` 等，逐个加回
> - **绝不要**在 PATH 里留空的 `;;` 或结尾分号——会让命令搜索乱掉

验证（**下面按终端分开写，只挑你在用的那一个抄**）：

```bash
# —— Git Bash(推荐) ——
gcc --version
# 应输出：gcc (GCC) 13.x.x 或类似
which gcc
# 应输出：/c/dev/w64devkit/bin/gcc
where gcc            # 也可以，Git Bash 能调用这个 Windows 命令
# 应输出：C:\dev\w64devkit\bin\gcc.exe
```

```bat
rem —— cmd（命令提示符）——
gcc --version
rem 应输出：gcc (GCC) 13.x.x 或类似
where gcc
rem 应输出：C:\dev\w64devkit\bin\gcc.exe
```

```powershell
# —— PowerShell ——
gcc --version
# 应输出：gcc (GCC) 13.x.x 或类似
Get-Command gcc              # PowerShell 查命令位置要用 Get-Command
(Get-Command gcc).Source     # 只要完整路径
# 应输出：C:\dev\w64devkit\bin\gcc.exe
where.exe gcc                # 也可以：显式调用 cmd 的 where（注意 .exe）
```

> [!warning] PowerShell 里敲 `where gcc` 会"什么都不输出"（本章最容易卡住的一步）
> **现象**：`gcc --version` 正常打印版本号，但 `where gcc` 一片空白，**也不报错**。
> 你会怀疑 PATH 没配好，然后反复重装——但问题根本不在 PATH。
>
> **原因**：`where` 是 **cmd 的命令**。在 PowerShell 里，`where` 是 `Where-Object` 的**别名**
> （用于过滤管道对象）。你没给它管道输入，它就安静地不做事。
>
> | 想查命令位置 | cmd | PowerShell | Git Bash |
> |---|---|---|---|
> | 正确写法 | `where gcc` | `Get-Command gcc` | `which gcc` |
> | 兼容写法 | — | `where.exe gcc` | `where gcc` |
> | 只要完整路径 | `where gcc` | `(Get-Command gcc).Source` | `which gcc` |
>
> **通用技巧**：在 PowerShell 里想调用"cmd 的那条命令"，**加 `.exe` 后缀**即可绕过别名。
>
> 三个终端的完整对照表见 [[附录R-绝对零基础前置知识]] 第 3.2 节。

> [!tip] 推荐用 Windows Terminal
> Microsoft Store 里免费装。它比 cmd 好用太多：多标签、支持 UTF-8、能开 Git Bash。
> 装好后新建一个配置文件，命令行填 `C:\dev\w64devkit\bin\bash.exe`，就能直接用 Linux 风格终端。

## 先认识 C 程序长什么样

先别急着理解每一行的意思，只看它的**形状**：

```c
#include <stdio.h>

int main(void) {
    printf("Hello, KLBQ\n");
    return 0;
}
```

这段代码里有两类最基本、出现频率最高的符号，先认清它们：

| 符号 | 作用 | 类比 |
|---|---|---|
| `{ }` 花括号 | 圈出一个"块"——一组语句的集合 | 一个盒子，里面的东西都属于它 |
| `;` 分号 | 表示**一条语句结束** | 中文的句号 |

**先记住两条铁律**：

1. **每条语句末尾必须写 `;`**。忘了写，编译立刻报错。
2. **花括号 `{` 和 `}` 必须成对出现**。左边一个开，右边一个闭。

> [!tip] 缩进不影响运行
> 代码前面的空格（缩进）只是给人看的，编译器不在乎。
> 但**养成缩进习惯**能让你一眼看出"哪条语句属于哪个块"。本项目全程用 4 个空格缩进。

## 逐行逐符号拆解

### 第 1 行：`#include <stdio.h>`

```c
#include <stdio.h>
```

作用：**把 `stdio.h` 这个文件的内容，原封不动"粘"到这一行的位置。**

"stdio" = **st**andard **i**nput **o**utput（标准输入输出），`.h` 是 "header（头文件）" 的缩写。

为什么需要它？因为后面要用 `printf`，而 `printf` 的"说明书"就写在 `stdio.h` 里。不 `#include`，编译器不认识 `printf`，会报错。

> [!note] `#` 开头的行很特殊
> `#` 开头的行叫"预处理指令"，它们**不是 C 代码**，而是给"预处理器"（编译第一步，第 03 章讲）看的命令。
> `#include` 就是"把那个文件拿过来"。第 09 章会把这件事讲透。
> **现在只要记住：要用 `printf`，就写 `#include <stdio.h>`。**

### 第 3 行：`int main(void)`

```c
int main(void)
```

这是**程序入口**。操作系统加载你的程序后，第一个执行的函数就是 `main`。拆开看：

| 部分 | 含义 |
|---|---|
| `int` | **返回值类型**——函数结束时，要"交回"一个整数给操作系统 |
| `main` | **函数名**——这个名字固定，操作系统认的就是它 |
| `(void)` | **参数列表**——`void` 表示这个函数**不接受任何参数** |

> [!important] 为什么入口必须叫 `main`
> C 程序的入口名**必须叫 `main`**，这是标准规定。
> 写成 `Main`、`mian`、`start`，系统都找不到入口，链接时就会报 `undefined reference to 'main'`（第 03 章会再见到）。

### 第 4 行：`{` —— 函数体的开始

```c
{
```

花括号 `{` 表示"**下面这些语句，都属于 `main` 这个函数**"。

从 `{` 到对应的 `}`，中间所有内容就是函数的**函数体**——"这个函数具体要做什么"。

### 第 5 行：`printf("Hello, KLBQ\n");`

```c
printf("Hello, KLBQ\n");
```

这是"真正干活"的一行——把一段字符串输出到屏幕。逐段拆：

```text
printf  (  "Hello, KLBQ\n"  )  ;
└──┬─┘  │  └──────┬──────┘  │  │
   │    │         │         │  └─ 分号：这条语句到此结束
   │    │         │         └──── 圆括号：放"参数"
   │    │         └────────────── 双引号：表示这是一段"字符串"
   │    └──────────────────────── 圆括号的开头
   └───────────────────────────── 函数名 printf（print formatted，格式化打印）
```

| 符号 | 意思 |
|---|---|
| `printf` | 一个**函数**的名字（功能：把内容打印出来） |
| `(...)` | 圆括号里放**参数**（传给函数的信息）。这里只有一个参数 |
| `"..."` | **双引号**包起来的叫**字符串**——一串字符 |
| `\n` | **转义序列**：`\` 加 `n` 代表"换行" |
| `;` | 一条语句结束，必须写 |

#### 什么是字符串

字符串就是"**一串字符**"，用**双引号**包起来，例如：`"Hello"`、`"KLBQ"`、`"这是一个中文句子"`。
双引号之间的东西会被原样输出（除非遇到 `\` 转义）。

#### 什么是转义序列

有些字符**没法直接敲出来**（比如"换行"键、Tab 键），或者**本身有特殊含义**（比如双引号），就用 `\` 加一个字母表示：

| 写法 | 含义 |
|---|---|
| `\n` | 换行（**n**ewline） |
| `\t` | 制表符（一个 Tab） |
| `\\` | 一个真正的反斜杠 `\` |
| `\"` | 一个真正的双引号 `"`（它本身有特殊含义，所以得转义） |

所以 `printf("Hello, KLBQ\n");` 的输出是：

```text
Hello, KLBQ
```

末尾那个 `\n` 让光标换到下一行。**去掉 `\n` 试试看**，输出会紧挨着后面的东西（见下一节"动手改一改"）。

### 第 6 行：`return 0;`

```c
return 0;
```

意思是：**结束 `main` 函数，并"返回"整数 `0` 给操作系统。**

`return` 是"交回"的意思，后面跟的值就是"交回的东西"。

| 返回值 | 约定含义 |
|---|---|
| `0` | **成功**（一切正常） |
| 非 0（如 `1`、`-1`） | **失败**（出错了） |

这个约定很重要：别人（脚本、系统）运行你的程序时，可以通过返回值判断它有没有正常跑完。

### 第 7 行：`}` —— 函数体结束

```c
}
```

和开头那个 `{` 配对，表示 `main` 到这里结束。

**数一下**：这段程序里 `{` 有 1 个、`}` 有 1 个、`;` 有 2 个。**花括号必须配对，分号必须每条语句都有。**

## 完整对照图

把上面所有讲解合起来：

```c
#include <stdio.h>          // ← 预处理指令：把 printf 的说明书拿过来

int main(void) {            // ← 程序入口：int 返回值 / main 名字 / void 无参数
                            //   { 从这里开始，是 main 的函数体
    printf("Hello, KLBQ\n"); // ← 一条语句：调用 printf，输出字符串
    return 0;                // ← 一条语句：返回 0 给操作系统，表示"成功"
}                            // ← } 函数体结束
```

## 动手改一改：理解代码最有效的方式

**光看不会记住。** 打开 `hello.c`，按下面几步各改一次，每改一次重新编译运行，看输出怎么变。

### 练习 1：改文字

把 `Hello, KLBQ` 改成别的（比如你的名字）：`printf("Hello, 张三\n");`，编译运行看输出。

### 练习 2：去掉 `\n`

改成 `printf("Hello, KLBQ");`，再在后面加一行 `printf("第二行\n");`，看输出变成什么样。
你会看到两句话**连在一起**了——这就是 `\n` 的作用。

### 练习 3：加一行输出

在 `printf` 后面、`return` 前面再加一行 `printf("我是第二行\n");`，重新编译运行。

### 练习 4：故意删掉一个分号

把 `printf("Hello, KLBQ\n")` 末尾的 `;` 删掉，重新编译。你会看到类似这样的报错：

```text
error: expected ';' before 'return'
```

**看第一行报错就够，后面往往是连锁反应。** 这是你第一次主动制造编译错误——第 16 章会系统讲怎么读报错。

### 练习 5：故意拼错 `main`

把 `main` 改成 `mian`，重新编译，看报错：

```text
undefined reference to `main'
```

理解"入口名必须叫 main"。

> [!tip] 做完这 5 个练习，你才算真的会了本章
> 只读不做的人，到第 04 章就会卡住。
> **改错的体验比看对的讲解更值钱。**

## 编译命令拆解

```
gcc hello.c -o hello.exe
└┬┘ └──┬──┘ └──┬──┘ └───┬───┘
 │     │       │        └─ 输出文件名
 │     │       └─ -o = output，指定输出
 │     └─ 源文件
 └─ 编译器
```

不加 `-o` 的话，Windows 上默认生成 `a.exe`。

> [!note] 加上警告选项，从第一天开始
> 以后都用这个命令：
> ```bash
> gcc -Wall -Wextra hello.c -o hello.exe
> ```
> `-Wall` 打开常用警告，`-Wextra` 打开额外警告。
> 编译器警告是你最便宜的老师——它能在程序运行前就告诉你哪里写错了。
> 本项目 `Application.mk` 里就是这么干的（第 34 章会讲）。

## 常见错误对照表

| 报错 | 原因 | 解法 |
|---|---|---|
| `'gcc' 不是内部或外部命令` | PATH 没生效 | 重开终端；检查路径拼写 |
| **`where gcc` 什么都不输出，也不报错** | **你在 PowerShell 里**（`where` 在 PowerShell 是 `Where-Object` 别名）| 改用 `Get-Command gcc` 或 `where.exe gcc` |
| `fatal error: stdio.h: No such file` | 装的是不完整工具链 | 换 w64devkit |
| `undefined reference to 'main'` | 没写 main 函数 / 拼错 | 检查 `int main` |
| 中文输出乱码 | 终端编码不一致 | cmd / PowerShell 里敲 `chcp 65001`；Git Bash 里设 `export LANG=zh_CN.UTF-8`；或改用 Windows Terminal |
| `No such file or directory` 但文件明明在 | 路径含中文/空格，或把 `.exe` 安装包改到了自定路径 | 按本章开头的三条规矩重装/挪位 |
| VS Code 里插件找不到编译器 | 装 VS Code 时改了安装路径 | 卸掉重装，**用默认路径** |
| 命令找不到，但同一条命令别人能用 | **终端用错了**（cmd / PowerShell / Git Bash 命令不通用）| 看报错语种反推终端，见 [[附录R-绝对零基础前置知识]] 3.2 节 |
