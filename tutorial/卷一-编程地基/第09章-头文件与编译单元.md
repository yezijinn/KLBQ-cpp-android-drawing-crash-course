# 第 09 章 · 头文件与编译单元

> [!abstract] 本章目标
> 搞清楚 `.h` 和 `.cpp` 到底怎么分工，为什么本项目有些"头文件"里写了函数实现，
> 以及 `#include` 背后那次真实的文本粘贴。

## 先看一次真实的"粘贴"

```c
// add.h
int add(int a, int b);
```

```c
// main.c
#include "add.h"
#include "add.h"        // 故意包含两次
int main(void) { return add(1, 2); }
```

```c
// add.c
#include "add.h"
int add(int a, int b) { return a + b; }
```

跑 `gcc -E main.c -o main.i`，打开 `main.i` 看：`int add(int a, int b);` 出现了**两次**。
`#include` 就是纯文本粘贴，没有任何"已包含过就跳过"的逻辑。

那为什么没报错？因为**声明**可以重复，定义不行。

| 可以重复 | 不能重复 |
|---|---|
| 函数声明 `int add(int,int);` | 函数定义 `int add(int a,int b){...}` |
| `extern int x;` | `int x;`（全局变量定义） |
| 结构体定义？**不能** | 同一编译单元里结构体只能定义一次 |

所以第三条需要 `#pragma once`（见下）。

## 编译单元（Translation Unit）

**一个 `.c`/`.cpp` 文件，加上它 `#include` 进来的所有头文件，展开后构成的整体，叫一个编译单元。**

编译器一次只处理一个编译单元，编译完生成一个 `.o`。它不知道别的编译单元里有什么。

```
main.cpp + draw.h + driver.h + imgui.h  ──编译──>  main.o
draw_Gui.cpp + 同样的头文件              ──编译──>  draw_Gui.o
                                                     │
                                              链接器 ──> 可执行文件
```

这就是为什么 `main.cpp` 里用 `UpdateGameData()`（定义在 `draw_Gui.cpp`）也能编译通过：
编译时它只看到 `draw.h` 里的声明，地址留空；链接时才填。

## .h 里放什么，.cpp 里放什么

| 放 `.h` | 放 `.cpp` |
|---|---|
| 函数**声明** | 函数**定义**（函数体） |
| 结构体/类**定义** | 成员函数的实现 |
| `extern` 变量声明 | 全局变量定义 |
| 宏、`inline` 函数、模板 | 静态内部函数 |
| `constexpr` 常量 | |

一个对照（本项目的 `GameTools`）：

```cpp
// include/My_Utils/GameTools.h   ← 只有声明
namespace GameTools {
    extern Vec2 ScreenSize;
    extern Matrix WorldMatrix;
    Matrix rotatorToMatrix(Rotator rotation);
    void WorldToScreen(Vec2 *bscreen, Vec3 *obj);
}
```

```cpp
// src/My_Utils/GameTools.cpp     ← 实现
namespace GameTools {
    Vec2 ScreenSize;                     // 定义（对应 extern 声明）
    Matrix WorldMatrix;

    Matrix rotatorToMatrix(Rotator rotation) {
        /* 40 行实现 */
    }
}
```

> [!danger] `extern` 声明 ≠ 定义
> ```cpp
> extern Vec2 ScreenSize;    // 声明：别处有个这个变量
> Vec2 ScreenSize;           // 定义：真的在这里分配内存
> ```
> 如果把定义写进 `.h`，每个包含它的 `.cpp` 都会各建一份，链接时报 "multiple definition"。

## 为什么本项目很多实现写在 .h 里

你会看到 `SilentAim.h`、`TouchAim.h`、`PovAim.h`、`WorldToScreen.h` 全是**完整实现**，没有对应的 `.cpp`。
三种合法写法：

### 写法一：`inline` 函数

```cpp
// SilentAim.h
inline bool 写入角度(const Rotator &角) {
    dr->Write<float>(AppBase.PlayerController + 0x378, 角.Pitch);
    return true;
}
```

`inline` 函数的定义可以出现在多个编译单元（链接器会合并重复的实例）。

### 写法二：`inline` 变量（C++17）

```cpp
inline AimConfig Cfg;      // 头文件里的全局变量，全程序只有一份
inline float px = 0.0f;    // WorldToScreen.h 里就是这么写的
```

C++17 之前，头文件里不能定义全局变量。C++17 的 `inline` 变量解决了这个问题。
**这就是为什么 `Application.mk` 里写 `-std=c++17`（实际模块编译用 c++20）。**

### 写法三：模板必须放头文件

```cpp
template <typename T> T Read(uint64_t address) { ... }
```

模板不是代码，是"生成代码的配方"。编译器在看到 `Read<float>(...)` 时才生成具体代码。
所以它必须在头文件里，否则别的编译单元看不到配方。

## #pragma once 与 include guard

问题：`a.h` 包含 `c.h`，`b.h` 也包含 `c.h`，`main.cpp` 同时包含 `a.h` 和 `b.h`
→ `c.h` 被粘贴两次 → 结构体重复定义 → 报错。

解法一（现代，推荐）：

```cpp
#pragma once
```

解法二（传统，兼容性最好）：

```cpp
#ifndef MY_UTILS_GAMETOOLS_H
#define MY_UTILS_GAMETOOLS_H
/* ... */
#endif
```

本项目两种都在用（`driver.h` 用 `#pragma once`，`SysHal.h` 用 include guard）。

> [!note] `#pragma once` 的边界情况
> 同一份文件通过不同路径（软链接、网络路径）被包含时，编译器可能认不出是同一个文件。
> 老工程更倾向 include guard。新项目用 `#pragma once` 就行。
> 本项目 `variable.h` 就踩过类似的坑——它是"实现写在头文件里"的历史写法。

## 声明与定义分离的好处

1. **编译更快**：改 `.cpp` 只需重编一个文件；改 `.h` 会触发所有包含它的文件重编。
2. **隐藏实现**：给别人 `.h` + `.a`，他看不到你的源码。（本项目分发 Embree 就是这形式）
3. **解耦**：`main.cpp` 不关心 `draw_Gui.cpp` 怎么写。

代价：跳转时要切文件，IDE 的"转到定义"功能就是干这个的。

## 一个反例：variable.h 的教训

本项目 `src/Android_draw/variable.h` 里有：

```cpp
bool permeate_record_ini = false;      // 全局变量定义
float FPS = 120.0f;
std::unique_ptr<AndroidImgui> graphics;
int abs_ScreenX = 0, abs_ScreenY = 0;
```

这是**在头文件里定义全局变量**（非 inline）。它现在能编译，是因为只有 `draw_Gui.cpp`
一个编译单元包含了它。如果哪天第二个 `.cpp` 也 `#include "variable.h"`，
立刻报 `multiple definition of 'abs_ScreenX'`。

正确写法应该是：

```cpp
// variable.h
#pragma once
extern bool permeate_record_ini;
extern int abs_ScreenX, abs_ScreenY;

// variable.cpp
bool permeate_record_ini = false;
int abs_ScreenX = 0, abs_ScreenY = 0;
```

> [!question] 思考题
> 为什么 `draw.h` 里写 `extern long int Uworld;` 而 `variable.h` 里写 `long int Uworld = 0;`？
> 哪个是正确做法？
> <br>答案：`draw.h` 的 `extern` 声明是正确做法；`variable.h` 的定义写法是隐患。
> 前者被多个文件包含也安全，后者只能被一个文件包含。

## 项目里的 include 路径

`Android.mk` 里这么配：

```makefile
LOCAL_C_INCLUDES += $(LOCAL_PATH)/include
LOCAL_C_INCLUDES += $(LOCAL_PATH)/include/Android_draw
LOCAL_C_INCLUDES += $(LOCAL_PATH)/include/Hack
```

配了之后，代码里就能这么写：

```cpp
#include "draw.h"           // 实际在 include/Android_draw/
#include "Hack.h"           // 实际在 include/Hack/
#include "MemDriver.h"      // 实际在 include/My_Utils/
```

而不用写 `#include "Android_draw/draw.h"`。好处是移动文件时不用改所有 include。

## 两种 include 写法的区别

```cpp
#include <imgui.h>       // 尖括号：只在系统/指定的 include 路径里找
#include "draw.h"        // 引号：先在当前文件目录找，找不到再去系统路径
```

本项目混用两种，因为都配了 `-I`，实际效果相同。建议：
- 项目自己的头文件用 `"xxx.h"`
- 第三方/系统头文件用 `<xxx.h>`

## 动手：拆一个单文件程序

把下面的单文件拆成 `vec.h` + `vec.cpp` + `main.cpp` 三份，并用 Makefile 编译：

```c
#include <stdio.h>
#include <math.h>

struct Vec3 { float x, y, z; };

float length(struct Vec3 v) { return sqrtf(v.x*v.x + v.y*v.y + v.z*v.z); }
struct Vec3 normalize(struct Vec3 v) {
    float l = length(v);
    struct Vec3 r = {v.x/l, v.y/l, v.z/l};
    return r;
}

int main(void) {
    struct Vec3 v = {3, 4, 0};
    struct Vec3 n = normalize(v);
    printf("len=%f  n=(%f,%f,%f)\n", length(v), n.x, n.y, n.z);
}
```

要求：
- `vec.h` 放结构体定义 + 两个函数声明 + `#pragma once`
- `vec.cpp` 放实现
- `main.cpp` 只 `#include "vec.h"`
- 编译：`gcc -c vec.cpp -o vec.o && gcc -c main.cpp -o main.o && gcc vec.o main.o -lm -o app`

注意 `-lm`：数学库要显式链接，这也是常见的 `undefined reference` 来源。
