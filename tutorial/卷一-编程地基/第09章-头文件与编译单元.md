# 第 09 章 · 头文件与编译单元

> [!abstract] 本章目标
> 搞清楚 `.h` 和 `.cpp` 到底怎么分工，为什么本项目有些"头文件"里写了函数实现，
> 以及 `#include` 背后那次真实的文本粘贴。

## 先搞清"为什么要拆文件"

到目前为止，你写的程序都是**一个 `.c` 文件**。写完编译，完事。

但真实的程序不可能都塞在一个文件里。想想本项目：

- 驱动层：`driver.h`（1300 行）、`SysHal.h`、`MemDriver.h`
- 数据解析：`draw_Gui.cpp`、`GameTools.cpp`
- 自瞄三套：`SilentAim.h`、`PovAim.h`、`TouchAim.h`
- 图形：`VulkanGraphics.cpp`、`AndroidImgui.cpp`、ImGui 全套
- 物理：`PhysX.h`（1800 行）

**所有这些加起来几万行。** 全塞进一个文件会怎样？

| 问题 | 后果 |
|---|---|
| 文件太大 | 编辑器卡顿，定位困难 |
| 编译太慢 | 改一行要重编几万行 |
| 无法协作 | 两个人同时改一个文件，冲突不断 |
| 无法复用 | 想借用某个功能，得把整个文件抱走 |

**所以真实工程必然拆成多个文件。** 这一章讲的就是：拆成多文件后，怎么组织、怎么编译、`.h` 和 `.c` 各放什么。

### 一个最小多文件工程

假设你要写一个"计算器"程序，功能有加法和减法。拆成三个文件：

**`calc.h`** —— 头文件，放"声明"：

```c
// calc.h
int add(int a, int b);
int sub(int a, int b);
```

**`calc.c`** —— 实现文件，放"定义"：

```c
// calc.c
#include "calc.h"

int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }
```

**`main.c`** —— 主程序，用到加法和减法：

```c
// main.c
#include <stdio.h>
#include "calc.h"

int main(void) {
    printf("%d\n", add(3, 4));   // 输出 7
    printf("%d\n", sub(10, 3));  // 输出 7
    return 0;
}
```

**编译**（分两步，第 03 章讲过原理）：

```bash
gcc -c calc.c -o calc.o       # 编译 calc.c 成目标文件
gcc -c main.c -o main.o       # 编译 main.c 成目标文件
gcc calc.o main.o -o calc.exe # 链接成一个可执行文件
./calc.exe
```

或者一步到位（编译器自动分步再链接）：

```bash
gcc calc.c main.c -o calc.exe
```

### 三文件各是什么角色

| 文件 | 叫什么 | 放什么 | 谁需要它 |
|---|---|---|---|
| `calc.h` | 头文件 | **声明**（"有这么一个函数"） | `calc.c` 和 `main.c` 都 `#include` 它 |
| `calc.c` | 源文件 / 实现文件 | **定义**（函数体） | 编译成 `calc.o` |
| `main.c` | 主源文件 | 程序入口和业务逻辑 | 编译成 `main.o` |

**核心问题**：`main.c` 里调用 `add(3, 4)`，但 `add` 的函数体在 `calc.c` 里。`main.c` 怎么知道 `add` 长什么样？

**答案**：`main.c` `#include "calc.h"`，看到声明 `int add(int a, int b);`，就知道"有个函数叫 add，接受两个 int，返回 int"。**它不需要看 `calc.c`。**

真正找到 `add` 的地址、把调用点填对，是**链接阶段**干的事（第 03 章讲过）。

**这就是这一章要讲的核心机制**：编译时看声明（头文件），链接时找定义（.o 文件）。

## `.h` 和 `.c` 的分工原则

**记住一句话**：

> **头文件放"是什么"，源文件放"怎么做"。**

具体展开：

| 内容 | 放哪 | 为什么 |
|---|---|---|
| 函数**声明** | `.h` | 别人要知道"有这个函数"才能调用 |
| 函数**定义**（函数体） | `.c` | 实现细节，别人不需要看 |
| 结构体 / 类的**定义** | `.h` | 用这个类型的代码需要知道它长什么样 |
| 全局变量 `extern` 声明 | `.h` | 告诉编译器"这个变量在别处定义" |
| 全局变量**定义** | `.c` | 只在**一个** `.c` 里分配内存 |
| 宏 `#define` | `.h` | 用到宏的地方需要看到 |

> [!important] 为什么"全局变量定义"必须只在一个 `.c` 里
> 如果 `.h` 里写 `int counter = 0;`，而这个 `.h` 被 3 个 `.c` 包含，
> 每个 `.c` 都会**创建一个 counter**，链接时会报 `multiple definition of 'counter'`。
> 正确做法：`.h` 里写 `extern int counter;`（声明），`.c` 里写 `int counter = 0;`（定义）。
> **本章后面会详解这个坑。**

## 一起看一次 `#include` 的真实效果

打开上面那个例子，把 `calc.h` 和 `main.c` 合并起来看：

**`main.c` 的真实内容**（原文）：

```c
// main.c
#include <stdio.h>
#include "calc.h"

int main(void) {
    printf("%d\n", add(3, 4));
    return 0;
}
```

**预处理后**（`gcc -E main.c -o main.i`，看 `main.i` 里 `main` 附近的内容）：

```c
// （stdio.h 和 calc.h 的内容被"粘贴"进来，展开后几百行）

// 来自 calc.h：
int add(int a, int b);
int sub(int a, int b);

int main(void) {
    printf("%d\n", add(3, 4));
    return 0;
}
```

**`#include "calc.h"` 这一行，被替换成了 `calc.h` 文件的完整内容。**

`#include` 做的事很简单：把那个文件的内容**原样抄过来**。它不是"引用"、不是"链接"，就是一次纯粹的文本复制。

**所以**：

- `#include` 之后的那一行 `int add(...)` 是**真的出现了**，不是"引用"
- 编译器在编译 `main.c` 时，看得到 `calc.h` 里的声明
- 但**看不到** `calc.c` 里的定义（那是另一个编译单元，第 03 章讲过）

**这就是多文件工程的整个机制**：每个 `.c` 通过 `#include` 头文件看到"接口"，各自编译成 `.o`，最后链接器把它们拼起来。


## 先看一次真实的"粘贴"

```c
// add.h
int add(int a, int b);
```

```c
// main.c
#include "add.h"
#include "add.h"        // 故意包含两次
int main(void) { return add(1, 2); }
```

```c
// add.c
#include "add.h"
int add(int a, int b) { return a + b; }
```

跑 `gcc -E main.c -o main.i`，打开 `main.i` 看：`int add(int a, int b);` 出现了**两次**。
`#include` 就是纯文本粘贴，没有任何"已包含过就跳过"的逻辑。

那为什么没报错？因为**声明**可以重复，定义不行。

| 可以重复 | 不能重复 |
|---|---|
| 函数声明 `int add(int,int);` | 函数定义 `int add(int a,int b){...}` |
| `extern int x;` | `int x;`（全局变量定义） |
| 结构体定义？**不能** | 同一编译单元里结构体只能定义一次 |

所以第三条需要 `#pragma once`（见下）。

## 编译单元（Translation Unit）

**一个 `.c`/`.cpp` 文件，加上它 `#include` 进来的所有头文件，展开后构成的整体，叫一个编译单元。**

编译器一次只处理一个编译单元，编译完生成一个 `.o`。它不知道别的编译单元里有什么。

```
main.cpp + draw.h + driver.h + imgui.h  ──编译──>  main.o
draw_Gui.cpp + 同样的头文件              ──编译──>  draw_Gui.o
                                                     │
                                              链接器 ──> 可执行文件
```

这就是为什么 `main.cpp` 里用 `UpdateGameData()`（定义在 `draw_Gui.cpp`）也能编译通过：
编译时它只看到 `draw.h` 里的声明，地址留空；链接时才填。

## .h 里放什么，.cpp 里放什么

| 放 `.h` | 放 `.cpp` |
|---|---|
| 函数**声明** | 函数**定义**（函数体） |
| 结构体/类**定义** | 成员函数的实现 |
| `extern` 变量声明 | 全局变量定义 |
| 宏、`inline` 函数、模板 | 静态内部函数 |
| `constexpr` 常量 | |

一个对照（本项目的 `GameTools`）：

> [!note] `namespace` 是什么
> 上面用到了 `namespace GameTools { ... }`——**命名空间**，用来给一组名字套一层"前缀"，避免和别的代码重名。
> 你以后会大量见到 `std::vector`、`std::string` 这种写法，`std` 就是标准库的命名空间。
> **第 11 章会专门讲命名空间。现在只要知道：`namespace 名字 { ... }` 是"把这些东西都装进这个名字下面"。**

```cpp
// include/My_Utils/GameTools.h   ← 只有声明
namespace GameTools {
    extern Vec2 ScreenSize;
    extern Matrix WorldMatrix;
    Matrix rotatorToMatrix(Rotator rotation);
    void WorldToScreen(Vec2 *bscreen, Vec3 *obj);
}
```

```cpp
// src/My_Utils/GameTools.cpp     ← 实现
namespace GameTools {
    Vec2 ScreenSize;                     // 定义（对应 extern 声明）
    Matrix WorldMatrix;

    Matrix rotatorToMatrix(Rotator rotation) {
        /* 40 行实现 */
    }
}
```

> [!danger] `extern` 声明 ≠ 定义
> ```cpp
> extern Vec2 ScreenSize;    // 声明：别处有个这个变量
> Vec2 ScreenSize;           // 定义：真的在这里分配内存
> ```
> 如果把定义写进 `.h`，每个包含它的 `.cpp` 都会各建一份，链接时报 "multiple definition"。

## 为什么本项目很多实现写在 .h 里

你会看到 `SilentAim.h`、`TouchAim.h`、`PovAim.h`、`WorldToScreen.h` 全是**完整实现**，没有对应的 `.cpp`。
三种合法写法：

### 写法一：`inline` 函数

```cpp
// SilentAim.h
inline bool 写入角度(const Rotator &角) {
    dr->Write<float>(AppBase.PlayerController + 0x378, 角.Pitch);
    return true;
}
```

`inline` 函数的定义可以出现在多个编译单元（链接器会合并重复的实例）。

### 写法二：`inline` 变量（C++17）

```cpp
inline AimConfig Cfg;      // 头文件里的全局变量，全程序只有一份
inline float px = 0.0f;    // WorldToScreen.h 里就是这么写的
```

C++17 之前，头文件里不能定义全局变量。C++17 的 `inline` 变量解决了这个问题。
**这就是为什么 `Application.mk` 里写 `-std=c++17`（实际模块编译用 c++20）。**

### 写法三：模板必须放头文件

```cpp
template <typename T> T Read(uint64_t address) { ... }
```

模板不是代码，是"生成代码的配方"。编译器在看到 `Read<float>(...)` 时才生成具体代码。
所以它必须在头文件里，否则别的编译单元看不到配方。

## #pragma once 与 include guard

问题：`a.h` 包含 `c.h`，`b.h` 也包含 `c.h`，`main.cpp` 同时包含 `a.h` 和 `b.h`
→ `c.h` 被粘贴两次 → 结构体重复定义 → 报错。

解法一（现代，推荐）：

```cpp
#pragma once
```

解法二（传统，兼容性最好）：

```cpp
#ifndef MY_UTILS_GAMETOOLS_H
#define MY_UTILS_GAMETOOLS_H
/* ... */
#endif
```

本项目两种都在用（`driver.h` 用 `#pragma once`，`SysHal.h` 用 include guard）。

> [!note] `#pragma once` 的边界情况
> 同一份文件通过不同路径（软链接、网络路径）被包含时，编译器可能认不出是同一个文件。
> 老工程更倾向 include guard。新项目用 `#pragma once` 就行。
> 本项目 `variable.h` 就踩过类似的坑——它是"实现写在头文件里"的历史写法。

## 声明与定义分离的好处

1. **编译更快**：改 `.cpp` 只需重编一个文件；改 `.h` 会触发所有包含它的文件重编。
2. **隐藏实现**：给别人 `.h` + `.a`，他看不到你的源码。（本项目分发 Embree 就是这形式）
3. **解耦**：`main.cpp` 不关心 `draw_Gui.cpp` 怎么写。

代价：跳转时要切文件，IDE 的"转到定义"功能就是干这个的。

## 一个反例：variable.h 的教训

本项目 `src/Android_draw/variable.h` 里有：

```cpp
bool permeate_record_ini = false;      // 全局变量定义
float FPS = 120.0f;
std::unique_ptr<AndroidImgui> graphics;
int abs_ScreenX = 0, abs_ScreenY = 0;
```

> [!note] `std::unique_ptr` 先当成"智能指针"看
> 第 3 行的 `std::unique_ptr<...>` 是 **C++ 的智能指针**（第 14 章会专门讲）——一种"会自动释放"的指针。
> 本节的重点不是它，而是**"在头文件里定义全局变量"这个反例**。看到 `std::unique_ptr` 先跳过即可。

这是**在头文件里定义全局变量**（非 inline）。它现在能编译，是因为只有 `draw_Gui.cpp`
一个编译单元包含了它。如果哪天第二个 `.cpp` 也 `#include "variable.h"`，
立刻报 `multiple definition of 'abs_ScreenX'`。

正确写法应该是：

```cpp
// variable.h
#pragma once
extern bool permeate_record_ini;
extern int abs_ScreenX, abs_ScreenY;

// variable.cpp
bool permeate_record_ini = false;
int abs_ScreenX = 0, abs_ScreenY = 0;
```

> [!question] 思考题
> 为什么 `draw.h` 里写 `extern long int Uworld;` 而 `variable.h` 里写 `long int Uworld = 0;`？
> 哪个是正确做法？
> <br>答案：`draw.h` 的 `extern` 声明是正确做法；`variable.h` 的定义写法是隐患。
> 前者被多个文件包含也安全，后者只能被一个文件包含。

## 项目里的 include 路径

`Android.mk` 里这么配：

```makefile
LOCAL_C_INCLUDES += $(LOCAL_PATH)/include
LOCAL_C_INCLUDES += $(LOCAL_PATH)/include/Android_draw
LOCAL_C_INCLUDES += $(LOCAL_PATH)/include/Hack
```

配了之后，代码里就能这么写：

```cpp
#include "draw.h"           // 实际在 include/Android_draw/
#include "Hack.h"           // 实际在 include/Hack/
#include "MemDriver.h"      // 实际在 include/My_Utils/
```

而不用写 `#include "Android_draw/draw.h"`。好处是移动文件时不用改所有 include。

## 两种 include 写法的区别

```cpp
#include <imgui.h>       // 尖括号：只在系统/指定的 include 路径里找
#include "draw.h"        // 引号：先在当前文件目录找，找不到再去系统路径
```

本项目混用两种，因为都配了 `-I`，实际效果相同。建议：
- 项目自己的头文件用 `"xxx.h"`
- 第三方/系统头文件用 `<xxx.h>`

## 动手：拆一个单文件程序

把下面的单文件拆成 `vec.h` + `vec.cpp` + `main.cpp` 三份，并用 Makefile 编译：

```c
#include <stdio.h>
#include <math.h>

struct Vec3 { float x, y, z; };

float length(struct Vec3 v) { return sqrtf(v.x*v.x + v.y*v.y + v.z*v.z); }
struct Vec3 normalize(struct Vec3 v) {
    float l = length(v);
    struct Vec3 r = {v.x/l, v.y/l, v.z/l};
    return r;
}

int main(void) {
    struct Vec3 v = {3, 4, 0};
    struct Vec3 n = normalize(v);
    printf("len=%f  n=(%f,%f,%f)\n", length(v), n.x, n.y, n.z);
}
```

要求：
- `vec.h` 放结构体定义 + 两个函数声明 + `#pragma once`
- `vec.cpp` 放实现
- `main.cpp` 只 `#include "vec.h"`
- 编译：`gcc -c vec.cpp -o vec.o && gcc -c main.cpp -o main.o && gcc vec.o main.o -lm -o app`

注意 `-lm`：数学库要显式链接，这也是常见的 `undefined reference` 来源。
