# 第 14 章 · 智能指针与生命周期

> [!abstract] 本章目标
> 不再手写 `new`/`delete`，能用 `unique_ptr`/`shared_ptr` 表达清楚"谁拥有这块内存"。
> 本项目用 `unique_ptr` 管理渲染器和网格数据。

> [!note] 承上
> 上一章用了 `vector`/`map` 这些"自动管理内存"的容器。
> 本章把这件事讲透：**用智能指针表达"谁拥有这块内存"**，不再手写 `new`/`delete`。

## 先看一个真实场景：内存泄漏排查

> [!question] 你遇到过这个吗？
> 程序跑几小时后内存越占越多，最后被系统杀掉——查半天发现是某处 `new` 之后忘了 `delete`。
> **根因**：裸指针管理堆内存，异常或提前返回时漏释放。
> 本章的 `unique_ptr` 让内存"自动归还"——从根上消灭泄漏。

## 先补：堆、栈与 `new` / `delete`

第 04 章简单提过"变量有四种存储期"，其中提到 **堆（heap）** 和 **栈（stack）**。
到这里必须把它讲清楚，因为智能指针就是用来管理**堆内存**的。

### 两种内存：栈和堆

**栈（stack）**：

```cpp
void f() {
    int x = 10;          // x 在栈上
    Player p;            // p 也在栈上
}                        // 函数返回，x 和 p 自动销毁
```

- 声明时**自动分配**
- 出了作用域（`}`）**自动销毁**
- **空间小**（几 MB —— MB 是兆字节，1 MB = 1024×1024 字节）
- **速度快**

**栈的局限**：只要出了作用域就没了。**想"活得比当前作用域更久"就需要堆。**

**堆（heap）**：

```cpp
Player *p = new Player();   // 在堆上分配一个 Player
// ... 用 p ...
delete p;                   // 手动销毁
```

- **手动分配**（`new`）
- **手动销毁**（`delete`）
- **空间大**（几百 MB 到几 GB）
- **速度慢一点**

### `new` 和 `delete` 的配对

```cpp
// 分配一个对象
Player *p = new Player();    // 在堆上创建一个 Player，返回它的地址
// ... 用 ...
delete p;                    // 销毁它，释放内存
```

```cpp
// 分配一个数组
int *arr = new int[100];     // 100 个 int
// ... 用 ...
delete[] arr;                // 注意是 delete[]，不是 delete！
```

> [!danger] `new` 必须配 `delete`，`new[]` 必须配 `delete[]`
> 忘了配 → **内存泄漏**（内存一直占着，直到程序结束）。
> 配错了（`new[]` 配 `delete`，或反过来）→ **未定义行为**，可能立刻崩，也可能潜伏很久。
> **这两个是 C++ 最经典的崩溃来源。**

### 为什么 `new` / `delete` 容易出错

看几个真实场景：

```cpp
// 场景 1：忘了 delete
void load() {
    Player *p = new Player();
    if (!p->init()) return;     // ← 提前 return，p 泄漏了
    use(p);
    delete p;                    // 只有正常路径才走到这
}

// 场景 2：异常导致泄漏
// （注：异常是 C++ 的错误处理机制，第 15 章会简单介绍。
//  现在只要理解"如果 process 中途出错跳走了，后面的 delete 就不会执行"。）
void load2() {
    Player *p = new Player();
    process(p);                  // 如果 process 抛异常，后面 delete 不执行
    delete p;
}

// 场景 3：双重释放
void load3() {
    Player *p = new Player();
    delete p;
    delete p;                    // 又删一次 → 崩
}

// 场景 4：悬空指针
void load4() {
    Player *p = new Player();
    delete p;                    // 已经释放
    p->hp = 100;                 // 还在用 → 崩
}
```

**这些错误的共同点**：`new` 和 `delete` 是"手动配对"的，人总会忘、会写错。

**C++ 的解法**：**智能指针（smart pointer）** —— 让"释放"这件事**自动发生**。

### 手动管理的痛点，智能指针来解决

| 手动 `new`/`delete` | 智能指针 |
|---|---|
| 忘记 `delete` → 泄漏 | 自动 delete |
| 提前 `return` → 泄漏 | 自动 delete |
| 异常 → 泄漏 | 自动 delete |
| 双重释放 → 崩 | 不可能发生 |
| 悬空指针 → 崩 | 作用域结束就销毁 |

**核心理念**：**让"对象销毁"这件事绑定到"作用域"，而不是绑定到"你记不记得写 delete"。**

这就是**RAII**思想（第 11 章讲过）在内存管理上的应用：

- 你在**栈上**创建一个 `unique_ptr` 对象
- `unique_ptr` 内部持有堆上对象的指针
- 当 `unique_ptr` **离开作用域被销毁**时，它的**析构函数自动调用 `delete`**

**你不用写 `delete`，因为栈对象的析构是自动的。** 一个自动的机制管一个自动的释放——完美。

## 先看一个泄漏

```cpp
void load_scene(void) {
    Mesh *m = new Mesh();
    if (!m->init()) return;      // ← 泄漏！没有 delete
    use(m);
    delete m;
}

void load_scene2(void) {
    Mesh *m = new Mesh();
    process(m);                  // 如果 process 抛异常 → 泄漏
    delete m;
}
```

C++ 没有垃圾回收。每个 `new` 都必须配一个 `delete`，而人总会忘。

## unique_ptr：独占所有权

```cpp
#include <memory>

void load_scene(void) {
    auto m = std::make_unique<Mesh>();     // C++14
    if (!m->init()) return;                // 自动 delete
    use(*m);
}                                          // 自动 delete
```

`unique_ptr` 语义：**这块内存归我，我是唯一的主人。我死了它就释放。**

### 三种用法

```cpp
// 1. 创建（推荐 make_unique，异常安全）
auto p = std::make_unique<Player>(100, 200);   // 参数传给构造函数

// 2. 像指针一样用
p->damage(10);
Player &ref = *p;

// 3. 判空
if (p) { ... }
p.reset();          // 主动释放
p.release();        // 放弃所有权，返回裸指针（少用）
```

### 不能拷贝，只能移动

```cpp
auto a = std::make_unique<Mesh>();
auto b = a;              // 编译错误！unique_ptr 不能拷贝
auto c = std::move(a);   // OK：所有权转移给 c，a 变成空
```

> [!note] `std::move` 是什么
> `std::move(a)` 不是"移动内存"，而是**一个类型转换**——它告诉编译器"**a 我不再用了，可以把它当'临时值'处理**"。
> 对于 `unique_ptr` 这种"只能有一个主人"的对象，用了 `std::move` 就允许"把所有权转走"。
> **结果**：`c` 拿到了所有权，`a` 变成空（`a == nullptr`）。
> 记法：**`std::move` = "这个东西我不要了，你拿走吧"**。

为什么不能拷贝？因为"唯一所有权"不允许有两个主人——否则谁负责 delete？

### 坏味道重构推演：从硬编码后端到工厂方法

> [!tip] 这段代码为什么不直接 new？
> 本项目 `GraphicsManager::getGraphicsInterface()` 只返回一个 `unique_ptr`，
> 看起来"多此一举"。**先看没有工厂时会写成什么样**，就懂了。

❌ **稚嫩写法：直接 new 具体类型**

```cpp
// ❌ 坏味道：main.cpp 里直接依赖具体后端
#include "VulkanGraphics.h"      // 业务入口 include 了具体实现
int main() {
    std::unique_ptr<AndroidImgui> graphics = std::make_unique<VulkanGraphics>();
    // 想换 OpenGL 后端？改这行 + 改 include + 重新编译所有依赖 main 的地方
    // 想在测试里用 FakeBackend？做不到——类型写死了
}
```

| 坏味道 | 后果 |
|---|---|
| 业务入口 include 具体实现 | 换后端要改 `main.cpp` 并重编 |
| `new VulkanGraphics` 写死 | 无法注入测试替身 |
| 创建逻辑散落 | 多处 new 时初始化参数不一致 |

✅ **优雅写法：工厂方法（本项目真实实现）**

```cpp
// ✅ GraphicsManager.h：声明只返回抽象接口
class GraphicsManager {
public:
    static std::unique_ptr<AndroidImgui> getGraphicsInterface();
};

// ✅ GraphicsManager.cpp：创建逻辑集中在一处（本项目真实源码）
std::unique_ptr<AndroidImgui> GraphicsManager::getGraphicsInterface() {
    return std::make_unique<VulkanGraphics>();
}

// ✅ main.cpp：只依赖抽象，不 include 具体后端
::graphics = GraphicsManager::getGraphicsInterface();
```

### 核心指标对比

| 维度 | ❌ 直接 new | ✅ 工厂方法 |
|---|---|---|
| **可维护性** | 换后端改多处 | 只改 `GraphicsManager.cpp` 一处 |
| **可扩展性** | 类型写死 | 加后端=加一个分支，调用方不变 |
| **单元测试** | 无法替换 | 可返回 Fake 后端 |
| **依赖方向** | main → VulkanGraphics | main → AndroidImgui 抽象 |

### 演进动因剖析

> [!note] 为什么本项目用工厂而不是直接 new？
> 1. **创建与使用分离**：`main.cpp` 只关心"拿到一个能画的接口"，
>    不关心它是 Vulkan 还是别的。
> 2. **集中创建点**：所有后端的构造细节收敛到 `GraphicsManager.cpp`，
>    初始化参数（窗口、队列族等）只在一处处理。
> 3. **配合抽象基类**：`AndroidImgui`（基类）定义了 `Create`/`Render`/`Shutdown` 等纯虚接口，
>    `VulkanGraphics`（派生类）实现——工厂返回基类指针，调用方零感知。
>
> **一句话**：工厂方法把"**创建什么**"和"**怎么用**"解耦，
> 这正是本项目 `graphics` 能是 `unique_ptr<AndroidImgui>`（而非具体类型）的原因。

再看看网格数据：

```cpp
// PhysX.h
std::vector<std::unique_ptr<TriangleMeshData>> mesh_datas;

// 返回时给裸指针（不转移所有权）
TriangleMeshData* GetGeomeoryData(unsigned int geomID) const {
    return mesh_datas[geomID].get();      // .get() 拿裸指针，所有权还在 vector
}
```

> [!note] `.get()` 的含义
> "我把指针借给你用一下，但所有权还是我的，你别 delete 它。"
> 这是 `unique_ptr` 和裸指针共存的常规方式。

## shared_ptr：共享所有权

```cpp
auto a = std::make_shared<Texture>();
auto b = a;        // OK：引用计数 +1，变成 2
// a 和 b 都失效后，对象才释放
```

内部维护一个引用计数。最后一个 `shared_ptr` 销毁时才 delete。

代价：
- 内存开销（控制块）
- 原子操作开销（线程安全计数）
- 循环引用风险（需要 `weak_ptr` 打破）

> [!tip] 优先 unique_ptr
> `shared_ptr` 方便，但也意味着"谁都能改这块内存"，生命周期变难推理。
> 90% 的场景 `unique_ptr` + 裸指针/引用传参就够了。
> 本项目**没有使用** `shared_ptr`——所有权关系明确，不需要共享。

## weak_ptr：打破循环引用

```cpp
struct Node {
    std::shared_ptr<Node> parent;
    std::shared_ptr<Node> child;
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->child = b;
b->parent = a;      // 循环引用！两个对象永远不会被释放
```

解法：让一方用 `weak_ptr`（不增加引用计数）：

```cpp
struct Node {
    std::weak_ptr<Node> parent;      // 不增加计数
    std::shared_ptr<Node> child;
};

if (auto p = parent.lock()) {        // lock() 得到 shared_ptr，可能为空
    use(p);
}
```

## 所有权语义速查

| 场景 | 用什么 |
|---|---|
| 独占，随作用域释放 | `unique_ptr` 或直接栈上对象 |
| 函数内部创建对象并返回 | `unique_ptr`（返回值） |
| 借用，不拥有 | 裸指针 `T*` 或引用 `T&` |
| 可选借用（可能为空） | 裸指针 `T*`，判空 |
| 多方共同拥有 | `shared_ptr`（谨慎） |
| 观察但不拥有 | `weak_ptr` |

> [!warning] 现代 C++ 的黄金法则
> **函数参数默认用引用或裸指针（表示"借用"），只有需要转移所有权时才用 `unique_ptr`。**
> ```cpp
> void draw(Mesh *m);                          // 借用，不 delete
> std::unique_ptr<Mesh> create_mesh();         // 转移所有权
> void store(std::unique_ptr<Mesh> m);         // 接收所有权
> ```

## 栈对象优先于堆对象

```cpp
// 不好：没必要用堆
auto *cfg = new Config();
/* ... */
delete cfg;

// 好：栈对象，自动管理
Config cfg;
/* ... */
```

只有三种情况需要堆：
1. 对象很大（栈只有几 MB）
2. 生命周期要跨出当前作用域
3. 大小/数量运行时才确定

## make_unique / make_shared 为什么更好

```cpp
// 不好
process(std::unique_ptr<Mesh>(new Mesh()), may_throw());
// 如果 may_throw() 先被求值并抛异常，new 出来的指针就泄漏了

// 好
process(std::make_unique<Mesh>(), may_throw());
// make_unique 一步完成，异常安全
```

另外 `make_shared` 只分配一次内存（对象+控制块合并），比 `shared_ptr<T>(new T)` 快。

## 数组版本

```cpp
auto buf = std::make_unique<uint8_t[]>(4096);     // unique_ptr<T[]>
buf[0] = 0xFF;

// 但大多数时候用 vector 更好
std::vector<uint8_t> buf2(4096);
```

## 自定义删除器

管理非 `new` 的资源（比如 `fopen` 的 `FILE*`、mmap 的内存）：

> [!note] `using FilePtr = ...;` 是什么
> 这是 C++ 的**类型别名**语法：**给一个复杂类型起个短名字**。
> `using FilePtr = std::unique_ptr<FILE, decltype(&fclose)>;` 的意思是"以后 `FilePtr` 就代表这一长串类型"。
> 它和 `typedef` 作用类似，但语法更清晰（`typedef` 第 07 章讲过）。
> `decltype(&fclose)` 是"取出 `&fclose` 的类型"——这样写就不用手写 fclose 的函数指针类型了。

```cpp
#include <cstdio>
#include <memory>

using FilePtr = std::unique_ptr<FILE, decltype(&fclose)>;

FilePtr open_file(const char *path, const char *mode) {
    FILE *fp = fopen(path, mode);
    return FilePtr(fp, &fclose);       // 析构时自动 fclose
}

// 用法
auto f = open_file("data.bin", "rb");
if (!f) { /* 打开失败 */ }
// 不用 fclose
```

也可以用 lambda：

```cpp
auto deleter = [](FILE *fp) { if (fp) fclose(fp); };
std::unique_ptr<FILE, decltype(deleter)> fp(fopen(path, "rb"), deleter);
```

## 本项目的资源管理检查

翻一遍 `main.cpp`：

```cpp
::window = android::ANativeWindowCreator::Create(...);
::graphics->Init_Render(::window, ...);

/* 主循环 */

Touch::Close();
graphics->Shutdown();
android::ANativeWindowCreator::Destroy(::window);
```

这里 `window` 是裸指针 `ANativeWindow*`，手动 `Destroy`。
这是 C 风格 API（Android NDK）的常规做法——NDK 给的就得按 NDK 的规则还。

可以包一层 RAII：

```cpp
struct WindowGuard {
    ANativeWindow *w = nullptr;
    ~WindowGuard() { if (w) android::ANativeWindowCreator::Destroy(w); }
};
```

这样即使主循环里抛异常或中途 return，窗口也能被正确销毁。

## 动手：把裸指针改造成 unique_ptr

```cpp
#include <cstdio>
#include <memory>
#include <vector>

struct Mesh {
    int id;
    std::vector<float> verts;
    Mesh(int i) : id(i) { printf("Mesh %d 构造\n", id); }
    ~Mesh() { printf("Mesh %d 析构\n", id); }
    void add(float v) { verts.push_back(v); }
};

// 改造前：可能泄漏
void old_way(void) {
    Mesh *m = new Mesh(1);
    m->add(1.0f);
    if (m->verts.empty()) return;     // 泄漏
    delete m;
}

// 改造后
void new_way(void) {
    auto m = std::make_unique<Mesh>(2);
    m->add(1.0f);
    if (m->verts.empty()) return;     // 打印"Mesh 2 析构"
}

// 容器持有所有权，函数借用
void inspect(const Mesh *m) {          // 借用：不 delete
    printf("  mesh %d 有 %zu 个顶点\n", m->id, m->verts.size());
}

int main(void) {
    std::vector<std::unique_ptr<Mesh>> meshes;
    meshes.emplace_back(std::make_unique<Mesh>(10));
    meshes.emplace_back(std::make_unique<Mesh>(20));
    meshes.back()->add(3.14f);

    for (const auto &m : meshes)
        inspect(m.get());              // .get() 借用

    meshes.clear();                    // 全部析构
    return 0;
}
```

跑起来观察构造/析构的打印顺序，确认没有泄漏。

### 习题 14.1 `unique_ptr` 自动释放（★）

**任务要求**：定义一个带构造/析构打印的 `Mesh` 类，用 `unique_ptr` 管理它，
验证离开作用域时析构**自动**被调用（不用手写 `delete`）。

**参考实现**：

```cpp
#include <cstdio>
#include <memory>
#include <cassert>

struct Mesh {
    int id;
    explicit Mesh(int i) : id(i) { printf("构造 Mesh %d\n", id); }
    ~Mesh() { printf("析构 Mesh %d\n", id); }
};

int main() {
    printf("--- 进入作用域 ---\n");
    {
        std::unique_ptr<Mesh> m = std::make_unique<Mesh>(1);
        assert(m && m->id == 1);
        // 不用手写 delete —— 离开这个 {} 时自动析构
    }
    printf("--- 已离开作用域 ---\n");
    printf("习题 14.1 通过\n");
    return 0;
}
```

**预期输出**：

```text
--- 进入作用域 ---
构造 Mesh 1
析构 Mesh 1        ← 离开 {} 时自动调用
--- 已离开作用域 ---
习题 14.1 通过
```

> [!tip] RAII 的核心
> `unique_ptr` 是栈对象，离开作用域时它的析构函数自动 `delete` 堆上的 `Mesh`。
> 这就是本项目 `graphics`（`std::unique_ptr<AndroidImgui>`）自动释放的原理。

### 习题 14.2 借用 vs 转移（★★）

**任务要求**：写两个函数——`void use(Mesh* m)`（借用，不取得所有权）和
`std::unique_ptr<Mesh> make(int id)`（转移所有权）。演示 `unique_ptr` 通过 `.get()` 借出裸指针后仍有效。

**参考实现**：

```cpp
#include <cstdio>
#include <memory>
#include <cassert>

struct Mesh {
    int id;
    explicit Mesh(int i) : id(i) {}
};

void use(Mesh* m) {                 // 借用：只看不用管释放
    if (m) printf("使用 Mesh %d\n", m->id);
}

std::unique_ptr<Mesh> make(int id) {  // 转移：返回所有权
    return std::make_unique<Mesh>(id);
}

int main() {
    auto m = make(42);              // 所有权在 m
    use(m.get());                   // ★ 借出裸指针，m 仍持有所有权
    assert(m && m->id == 42);       // m 依然有效
    printf("习题 14.2 通过\n");
    return 0;
}
```

> [!note] 传参约定
> - 参数要 **借用** → 传 `T*` 或 `T&`（如 `use(Mesh*)`）
> - 参数要 **转移所有权** → 传 `std::unique_ptr<T>`（按值）
> - **返回**新对象所有权 → 返回 `std::unique_ptr<T>`
> 本项目里 `dr->Read(...)` 传缓冲区用 `void*`（借用），而工厂函数返回 `unique_ptr`（转移）。
