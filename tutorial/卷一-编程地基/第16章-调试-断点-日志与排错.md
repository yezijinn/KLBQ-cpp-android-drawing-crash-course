### 三类错误：编译错误、链接错误、运行时错误

代码从写到运行要过三道关，每道关都可能出错：

| 类型 | 什么时候发现 | 典型现象 | 难度 |
|---|---|---|---|
| **编译错误** | 编译阶段 | 编译器报 `error:` | 最容易（编译器直接告诉你） |
| **链接错误** | 链接阶段 | 链接器报 `undefined reference` | 中等 |
| **运行时错误** | 程序运行时 | 崩溃、输出错误、卡死 | 最难（没有提示，只能自己找） |

**新手最怕第三类**，因为编译器不告诉你哪里错。**但三类都有套路，本章后面一个个讲。**

### 最重要的一条技能：读编译器报错

**编译器是你免费请的老师**——它在程序还没运行时就告诉你写错了。**学会看它的报错，能省掉 80% 的调试时间。**

#### 报错长什么样

```text
hello.c:5:16: error: expected ';' before 'return'
    5 |     printf("hi\n")
      |                   ^
      |                   |
      |                   这里缺少 ';'
```

**逐部分拆解**：

| 部分 | 含义 |
|---|---|
| `hello.c:5:16` | 文件名、**行号**、**列号**——去这个位置看 |
| `error:` | 严重错误，**编译停止**（还有 `warning:`，只是警告不停止） |
| `expected ';' before 'return'` | **错误原因**：在 return 之前缺少分号 |
| 下面的 `^` | **指向出问题的字符位置** |

#### 三条铁律：怎么读报错

**铁律 1：从第一条 error 开始看，不要看后面的。**

一个错误往往引发一串连锁报错。看第一条——**它才是真正的错因**。后面的可能是"因为前面错了，所以这里也错"。

**铁律 2：报错信息里提到了哪个行号，但问题往往在上一行。**

比如 `expected ';' before 'return'` 指向第 5 行 `return`，但**真正错的是第 4 行**——第 4 行末尾忘了分号，编译器处理到第 5 行才发现不对。

**铁律 3：报错语种能反推你在哪个终端（如果错误来自工具而非编译器）。**

这个第 02 章讲过：

| 报错形状 | 你在哪 |
|---|---|
| `'gcc' 不是内部或外部命令` | cmd |
| `无法将"gcc"项识别为...` | PowerShell |
| `bash: gcc: command not found` | Git Bash |

#### 常见的编译错误

| 报错信息 | 原因 | 解法 |
|---|---|---|
| `expected ';' before ...` | 上一行忘了分号 | 补上 `;` |
| `'xxx' undeclared` | 用了没声明的变量 / 拼错名字 | 检查拼写、检查声明位置 |
| `implicit declaration of function 'xxx'` | 用了没声明的函数 | `#include` 对应头文件，或自己声明 |
| `assignment makes integer from pointer without a cast` | 类型不对（指针赋给 int） | 检查类型 |
| `too few arguments to function` | 调用函数参数不够 | 补参数 |
| `stray '\357' in program` | 源文件编码问题（通常是有 BOM） | 保存为"UTF-8 无 BOM" |

> [!tip] 最便宜的调试工具：`-Wall -Wextra`
> **从第一天开始，编译时永远加 `-Wall -Wextra`**（第 02 章讲过）。
> ```bash
> gcc -Wall -Wextra hello.c -o hello.exe
> ```
> 它会把很多"不算错但很可疑"的代码**警告**出来——比如：
> - 变量声明了没用
> - `if (x = 5)`（本来想写 `==`）
> - 函数忘了返回值
> - 有符号/无符号比较
> **警告不是错误，但 90% 的警告都是隐患。能改就改掉。**

### 第二类：链接错误

链接错误典型长相：

```text
undefined reference to `add'
```

**含义**：编译没问题（声明看得到），但链接时找不到 `add` 的实现（定义）。

**三个常见原因**：

| 原因 | 现象 |
|---|---|
| **忘了把某个 `.o` 或 `.c` 加到编译命令** | 声明有，定义没编 |
| **忘了链接某个库**（如 `-lm`、`-lpthread`） | 用了库函数但没告诉链接器 |
| **函数名拼错** | 声明和定义的名字不一致 |

例：

```bash
# 错：忘了 calc.o
gcc main.o -o calc.exe
# 报 undefined reference to `add'

# 对：把 calc.o 加上
gcc main.o calc.o -o calc.exe
```

**链接顺序也有讲究**（第 03 章提过）：**依赖方放左边，被依赖方放右边。**

### 第三类：运行时错误

编译通过、链接通过，程序能跑起来，但**跑起来不对**：

- **崩溃**（段错误、Bus error、Aborted 等）
- **输出错**（数值不对、字符串乱码）
- **卡死**（无限循环、死锁）
- **偶发**（有时对有时错）

**这类问题没有编译器帮忙**，只能自己查。**本章后面每一层都是为它准备的。**

### 最重要的心法：先分类型，再选工具

**看到问题，第一反应应该是"这属于哪类"**：

```text
程序出问题
    │
    ├── 还没运行就报错？ → 编译/链接错误 → 看编译器/链接器的报错
    │
    ├── 一运行就崩溃？ → 段错误 → 看崩溃地址、查指针
    │
    ├── 能跑但输出错？ → 逻辑错误 → 加日志/断点，逐段排查
    │
    └── 有时对有时错？ → 竞态/未初始化 → 更难，先查未初始化变量
```

**分对类型，找因就快了。** 比如段错误十有八九是"空指针 + 偏移"，看一眼崩溃地址就能猜个七七八八。

### 段错误（SIGSEGV）是怎么回事

**段错误 = 访问了不该访问的内存。** 操作系统会把程序杀掉，报一个信号。

最常见的三种：

| 原因 | 代码 |
|---|---|
| **空指针解引用** | `int *p = nullptr; *p = 5;` |
| **空指针 + 偏移** | `uint64_t x = 0; Read(x + 0x30);` → 访问地址 `0x30`，崩 |
| **越界访问** | `int arr[3]; arr[100] = 5;` |

**崩溃信息里的 `fault addr 0x…` 是关键线索**——它告诉你"程序当时访问的是哪个地址"。

- `fault addr 0x0` → 纯空指针解引用
- `fault addr 0x30` → 空指针 + 偏移 0x30（**你沿着某个偏移链读数据，链断了**）
- `fault addr 0x…ff` 一类的奇怪值 → 可能是垃圾指针

**这条"看 fault addr 反推"的技能，是本章后面第四层"二进制分析"的核心。**

### 动手：故意制造三种错误

**目标**：亲手犯一遍，才能记住症状。

**练习 1（编译错误）**：故意写 `int a = 5` 忘了分号，编译，看报错在哪一行。

**练习 2（链接错误）**：写两个文件 `a.c`（`int foo();` 声明并调用）和 `b.c`（定义 `foo`），编译时**只编 a.c**，看 `undefined reference` 报错。

**练习 3（段错误）**：

```c
#include <stdio.h>

int main(void) {
    int *p = NULL;
    *p = 10;              // 崩
    return 0;
}
```

编译运行，看操作系统报什么（Windows 上是"程序无响应"，Linux/Android 上是 `Segmentation fault`）。

**做完三个练习，你对"三类错误"就有肌肉记忆了**——后面再看到类似的报错，立刻知道该往哪个方向查。


## 先看一个真实的崩溃

```
Signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x00000000000000a0
  #00 pc 0000000000012345  /data/local/tmp/klbq
```

`SIGSEGV` = 段错误 = 访问了不该访问的地址。`fault addr 0xa0` 说明你读了一个
接近 0 的地址——典型的**空指针 + 偏移**。

比如：

```cpp
uint64_t Uworld = 0;                        // 没读到
uint64_t Uleve = dr->Read<uint64_t>(Uworld + 0x30);  // 访问 0x30 → 崩
```

从 `0xa0` 反推：`0xa0 = 160 = 0x70 + 0x30`？还是某个结构体成员的偏移？
**看偏移值反推是哪一跳出错，是跨进程程序排错的核心技能。**

## 第一层：日志

### 分级

| 级别 | 用途 | 什么时候看 |
|---|---|---|
| ERROR | 出错，程序无法继续 | 总是看 |
| WARN | 可疑，但能继续 | 出问题时看 |
| INFO | 关键流程节点 | 排查流程时看 |
| DEBUG | 详细信息（每帧、每个对象） | 定位具体问题时临时开 |

本项目的日志宏（`driver.h`）：

```c
#define LS_LOGI_TAG(tag, fmt, ...) __android_log_print(ANDROID_LOG_INFO,  tag, fmt, ##__VA_ARGS__)
#define LS_LOGE_TAG(tag, fmt, ...) __android_log_print(ANDROID_LOG_ERROR, tag, fmt, ##__VA_ARGS__)
```

用法：

```cpp
LS_LOGI_TAG("Driver", "模块索引=%d 名称=%s 区段数量=%d", i, mod.name, mod.seg_count);
LS_LOGE_TAG("Dump", "无法创建 /sdcard/dump: %s", std::strerror(errno));
```

### 一定要带上上下文

```cpp
// 没用
LOG("failed");

// 有用
LS_LOGE_TAG("Driver", "GetModuleAddress 失败: name=%.*s seg=%d pid=%d",
            (int)moduleName.size(), moduleName.data(), segmentIndex, GetGlobalPid());
```

> [!tip] 打印 `string_view` 要用 `%.*s`
> `string_view` 不以 `\0` 结尾，不能用 `%s`（会读越界）。
> 正确写法：`printf("%.*s", (int)sv.size(), sv.data())`
> 本项目 `driver.h` 里全是这个写法。

### errno 是你的朋友

POSIX 系统调用失败时会设置 `errno`：

```cpp
#include <cerrno>
#include <cstring>

int fd = open("/data/Config", O_RDONLY);
if (fd < 0) {
    printf("打开失败: errno=%d (%s)\n", errno, std::strerror(errno));
}
```

常见 errno：

| errno | 含义 | 典型原因 |
|---|---|---|
| `EACCES` (13) | 权限不足 | 没 root、文件权限 |
| `ENOENT` (2) | 文件不存在 | 路径错 |
| `EFAULT` (14) | 地址无效 | 读越界 |
| `ESRCH` (3) | 进程不存在 | PID 失效 |
| `EPERM` (1) | 操作不允许 | SELinux |

Windows 上对应 `GetLastError()`。

## 第二层：断言

```cpp
#include <cassert>

void process(uint8_t *buf, size_t len) {
    assert(buf != nullptr && "buffer 不能为空");
    assert(len <= 4096 && "超过单页上限");
}
```

给 `assert` 加字符串提示（`"..." && 条件` 的写法）能让失败信息可读。

**发布版要关掉**：`-DNDEBUG`。本项目 `Application.mk` 用 `APP_OPTIM := release`，
NDK 会自动加 `-DNDEBUG`。

## 第三层：调试器

### GDB 基础命令

```bash
gcc -g -O0 main.c -o app        # -g 加调试信息，-O0 关优化
gdb ./app
```

| 命令 | 作用 |
|---|---|
| `b main` | 在 main 打断点 |
| `b file.c:42` | 在第 42 行打断点 |
| `r` | 运行 |
| `n` | 下一步（不进函数） |
| `s` | 下一步（进函数） |
| `c` | 继续到下一个断点 |
| `p x` | 打印变量 x |
| `p *ptr` | 打印指针指向的值 |
| `p/x addr` | 十六进制打印 |
| `x/16xb addr` | 查看 addr 开始的 16 字节（十六进制） |
| `bt` | 打印调用栈 |
| `info locals` | 显示所有局部变量 |
| `watch x` | x 被修改时停下 |

> [!warning] 优化会干扰调试
> `-O2` 下变量可能被优化掉，`p x` 会报 `optimized out`。
> 调试时用 `-O0`，发布才用 `-O2`。

### VS Code 图形化调试

装 C/C++ 插件后：
1. 侧栏"运行和调试" → 创建 `launch.json`
2. 选 `C++ (GDB/LLDB)`
3. 改 `program` 和 `miDebuggerPath`
4. F5 启动，点行号左边打断点

本项目 `.vscode/launch.json` 就是这个配置。

## 第四层：崩溃后的二进制分析

Android 原生崩溃会输出 tombstone。关键信息：

```
pid: 12345, tid: 12345, name: klbq  >>> /data/local/tmp/klbq <<<
signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x00000070
    x0  00000000000000a0  x1  0000000000000030
backtrace:
    #00 pc 000000000000f234  /data/local/tmp/klbq
```

定位到源码行：

```bash
aarch64-linux-android-addr2line -e klbq -f -C 0xf234
```

会输出 `函数名` 和 `文件:行号`。前提是产物**没被 strip**。

> [!note] 本项目 strip 了
> `APP_LDFLAGS := -flto -Wl,--gc-sections -s` 里的 `-s` 就是 strip。
> 调试阶段建议去掉 `-s`，或保留一份带符号的副本用于 addr2line。
> 第 41 章会详细讲符号管理。

## 第五层：系统化排错流程

遇到 bug 按这个顺序走，不要跳步：

```
1. 能复现吗？
   └─ 不能 → 加日志，记录触发条件（频率、时机、输入）
   
2. 报错信息是什么？
   └─ 段错误 → 空指针/越界（查地址值）
   └─ undefined reference → 链接问题（库没链、顺序错）
   └─ 编译错误 → 读第一行，往上看（后面的往往是连锁反应）
   
3. 定位到哪一行？
   └─ 二分法：注释掉一半代码，看问题还在不在
   └─ 或者：在关键路径上打日志，看执行到哪一步
   
4. 最小复现
   └─ 把问题抽出来写个 20 行的小程序
   └─ 90% 的情况下，写最小复现的过程中你就找到原因了
   
5. 验证修复
   └─ 改完必须重新跑原来的失败用例
   └─ 再跑一遍相关的成功用例（别改出新问题）
```

## 二分法实战

**场景**：程序启动就崩，不知道是哪一步。

```cpp
int main(void) {
    ConfigManager::LoadConfig();
    graphics = GraphicsManager::getGraphicsInterface();
    screen_config();
    window = Create(...);
    graphics->Init_Render(window, w, h);
    Touch::Init(...);
    while(flag) { ... }
}
```

做法：在这几行之间插 `printf("step %d\n", n);`，看崩在哪两个数之间。

或者更快：直接 `return 0;` 提前退出，逐个放开。

## 常见症状速查表

| 症状 | 最可能的原因 | 怎么确认 |
|---|---|---|
| 输出全是 0 | 地址算错，读到空洞 | 打印地址，看是不是 0 或极小值 |
| 输出是天文数字 | 类型错了（float 当 int 读） | 打印原始字节 hexdump |
| 时好时坏 | 未初始化变量 / 竞态 | 加 `-fsanitize=address` |
| 第一次对，后面错 | 缓存没更新 / 没判空 | 检查 `if (x == 0) return;` |
| 换个设备就崩 | 对齐 / 字长 / 字节序 | 检查 `sizeof`、指针类型 |
| 加了 printf 就不崩 | 竞态（时序被改变） | 用线程检查器，别靠 printf |
| 中文乱码 | 编码不一致 | 检查源文件 UTF-8、终端编码 |

## Sanitizer：自动找 bug 的工具

```bash
# 地址检查（越界、use-after-free、泄漏）
gcc -fsanitize=address -g main.c -o app

# 未定义行为检查
gcc -fsanitize=undefined -g main.c -o app

# 线程竞争检查
gcc -fsanitize=thread -g main.c -o app
```

跑起来后，它会**精确指出**哪一行越界、哪一行数据竞争，比你自己找快 100 倍。

```bash
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x...
READ of size 8 at 0x... thread T0
    #0 0x... in process /path/main.c:42
```

> [!warning] Sanitizer 会让程序慢 2~20 倍
> 只在调试时开。发布构建不要带。
> Android NDK 也支持（`-fsanitize=address`），需要额外的 runtime 库。

## 动手：用二分法定位一个 bug

下面这段代码有 bug（在某些输入下崩溃），用本章方法找出来：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>          // uint8_t

int find_marker(const uint8_t *data, size_t len) {
    for (size_t i = 0; i < len - 4; i++) {
        if (data[i] == 0xDE && data[i+1] == 0xAD &&
            data[i+2] == 0xBE && data[i+3] == 0xEF)
            return (int)i;
    }
    return -1;
}

int main(int argc, char **argv) {
    size_t n = argc > 1 ? atoi(argv[1]) : 16;
    uint8_t *buf = malloc(n);
    memset(buf, 0, n);
    if (n >= 4) { buf[n-4] = 0xDE; buf[n-3] = 0xAD; buf[n-2] = 0xBE; buf[n-1] = 0xEF; }
    printf("found at %d\n", find_marker(buf, n));
    free(buf);
    return 0;
}
```

提示：编译后试试 `app 3`、`app 0`、`app 1`（Git Bash 用 `./app 3`）。

<details>
<summary>答案（先自己找再展开）</summary>

`len - 4` 有**两个**问题：
1. 当 `len < 4` 时，`size_t`（无符号）下溢成巨大值，循环条件 `i < 巨大值` 永远成立 → 读越界 → 崩溃。
2. 即使 `len >= 4`，`i < len - 4` 也会**漏掉最后一个位置**（marker 在末尾 `len-4` 处时，`i` 最大只到 `len-5`，检查不到）——所以 `app 16` 明明有 marker 却返回 `-1`。

修法：
```cpp
if (len < 4) return -1;
for (size_t i = 0; i + 4 <= len; i++) { ... }
```

这正是第 04 章说的"无符号下溢"。用 `-fsanitize=address` 能立刻抓到。
</details>

## 课后习题

### 习题 16.1 用断言做前置检查（★）

**任务要求**：给一个除法函数加 `assert`，验证除零时能被拦住。

**参考实现**：

```c
#include <assert.h>
#include <stdio.h>

int safe_div(int a, int b) {
    assert(b != 0 && "除数不能为 0");   // 调试期拦住
    return a / b;
}

int main(void) {
    printf("%d\n", safe_div(10, 2));
    // safe_div(1, 0);  // 取消注释会触发断言，程序终止并打印失败位置
    printf("习题 16.1 通过\n");
    return 0;
}
```

> [!warning] assert 在 release（`-DNDEBUG`）下失效
> `assert` 只在调试期有效。生产代码里，参数校验要用显式 `if` + 返回错误码，
> 不能用 `assert`（否则 release 版本不会拦住非法输入）。
