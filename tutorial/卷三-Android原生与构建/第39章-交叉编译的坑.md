# 第 39 章 · 交叉编译的坑

> [!abstract] 本章目标
> 认识交叉编译里最常见的 8 个坑，知道每个坑的症状和解法。
> 本项目几乎所有编译问题都在这张表里。

## 什么是交叉编译

**在 A 机器上编译出能在 B 机器上运行的程序。**

| | 本机编译 | 交叉编译 |
|---|---|---|
| 编译平台（host） | x86_64 Windows | x86_64 Windows |
| 运行平台（target） | x86_64 Windows | **aarch64 Android** |
| 编译器 | `gcc` | `aarch64-linux-android21-clang` |

关键区别：**编译器知道目标平台的头文件、库、指令集，但不运行它。**

## 三个必须对齐的概念

| 概念 | 含义 | 本项目值 |
|---|---|---|
| **ABI** | 指令集 + 调用约定 + 二进制布局 | `arm64-v8a` |
| **API level** | 目标 Android 版本 | `android-25` |
| **STL** | C++ 标准库实现与链接方式 | `c++_static` |

三者任何一个不匹配，都会出诡异问题。

## 坑 1：ABI 不匹配

**症状**：

```
dlopen failed: "/data/local/tmp/app" has bad ELF magic
# 或
CANNOT LINK EXECUTABLE: ... is 32-bit instead of 64-bit
# 或
执行时直接 "No such file or directory"（其实是格式不对）
```

**原因**：编译出的架构和设备 CPU 不符。

**解法**：

```bash
adb shell getprop ro.product.cpu.abi        # arm64-v8a
adb shell getprop ro.product.cpu.abilist    # arm64-v8a,armeabi-v7a,armeabi
```

确认产物：

```bash
file app
# ELF 64-bit LSB executable, ARM aarch64, ...

readelf -h app | grep Machine
# Machine: AArch64
```

> [!note] 64 位设备能跑 32 位程序吗？
> 大部分能（有兼容层），但需要对应的 32 位库。
> 本项目只要 `arm64-v8a`，因为 Embree 的 `.a` 也只有 64 位版本。

## 坑 2：API level 太高或太低

**症状**：

```
error: 'ANativeWindow_...' is unavailable: introduced in API 26
# 或运行时
symbol lookup error: undefined symbol: ANativeWindow_...
```

**原因**：用了比 `APP_PLATFORM` 更新的 API，或者目标设备系统太老。

**两个方向的错误**：

| 方向 | 症状 | 解法 |
|---|---|---|
| API 设置太低 | 编译时 `is unavailable` | 提高 `APP_PLATFORM` |
| API 设置太高 | 老设备上找不到符号 | 降低，或用 `dlopen` + `dlsym` 动态获取 |

**最佳实践**：

```makefile
# 用你支持的最低版本编译，运行时再判断
APP_PLATFORM := android-25
```

运行时判断：

```cpp
#include <sys/system_properties.h>

int get_api_level() {
    char buf[PROP_VALUE_MAX];
    __system_property_get("ro.build.version.sdk", buf);
    return atoi(buf);
}

if (get_api_level() >= 29) {
    // 用新 API
} else {
    // 用老 API 或降级
}
```

本项目 `ANativeWindowCreator` 就是用这套逻辑按版本选符号（第 66 章）。

## 坑 3：STL 不一致

**症状**：

```
undefined reference to 'std::__ndk1::basic_string...'
# 或运行时
CANNOT LINK EXECUTABLE: cannot locate symbol "_ZNSt6__ndk1..."
```

**原因**：多个模块用了不同的 STL，或者静态/动态混用。

**规则**：一个工程里所有模块必须用**同一种** STL。

```makefile
APP_STL := c++_static     # 全局统一
```

| 值 | 命名空间 | 说明 |
|---|---|---|
| `c++_static` | `std::__ndk1` | libc++ 静态链接 |
| `c++_shared` | `std::__ndk1` | libc++ 动态链接 |
| `gnustl`（已删） | `std::__1` | 老版，NDK r18 后移除 |
| `system`（已删） | | 系统 STL，功能残缺 |

> [!danger] 静态库和主程序 STL 必须一致
> 如果你引入的第三方 `.a` 是用 `gnustl` 编的，
> 而你的工程用 `c++_static`，链接时会满屏 `undefined reference`。
> 唯一的解法是找到同 STL 的库版本，或让提供方重新编译。

## 坑 4：头文件在本地能找到，编译就找不到

**症状**：

```
fatal error: 'imgui.h' file not found
```

**原因**：本地 VS Code 的 IntelliSense 配置和 ndk-build 的实际配置是**两套**。

- VS Code 看 `.vscode/c_cpp_properties.json` 的 `includePath`
- ndk-build 看 `Android.mk` 的 `LOCAL_C_INCLUDES`

**解法**：两者都要配。

```json
// .vscode/c_cpp_properties.json
{
  "configurations": [{
    "name": "Android",
    "includePath": [
      "${workspaceFolder}/jni/include/**",
      "${env:NDK}/toolchains/llvm/prebuilt/windows-x86_64/sysroot/usr/include/**"
    ],
    "defines": ["__ANDROID_API__=25"]
  }]
}
```

> [!tip] 以 ndk-build 为准
> VS Code 的红波浪线只是参考。
> **真正能不能编译，看 `ndk-build` 的输出。**

## 坑 5：Windows 路径与换行符

**症状**：

```
make: *** No rule to make target 'src\main.cpp'
# 或
$'\r': command not found
```

**原因**：

| 问题 | 解法 |
|---|---|
| 反斜杠路径 | Makefile 里统一用 `/` |
| CRLF 换行 | 脚本/源码转 LF |

```bash
# 批量转 LF（Git Bash）
find . -name "*.sh" -exec dos2unix {} \;

# Git 配置，从源头避免
git config core.autocrlf input
```

## 坑 6：PIE 缺失

**症状**：

```
error: only position independent executables (PIE) are supported
```

**原因**：Android 5.0 起强制要求 PIE。

**解法**：现代 NDK 默认开启。如果手动关了，加回来：

```makefile
LOCAL_CFLAGS += -fPIE
LOCAL_LDFLAGS += -pie
```

## 坑 7：找不到系统库

**症状**：

```
ld: error: unable to find library -lfoo
```

**原因**：`-lfoo` 对应 `libfoo.so` 或 `libfoo.a`，但 NDK 的 sysroot 里没有。

**排查**：

```bash
ls $NDK/toolchains/llvm/prebuilt/*/sysroot/usr/lib/aarch64-linux-android/ | grep foo
```

可用的系统库（NDK 公开）：

```
liblog.so  libandroid.so  libz.so  libm.so  libdl.so
libEGL.so  libGLESv1_CM.so  libGLESv2.so  libGLESv3.so
libvulkan.so  libOpenSLES.so  libaaudio.so  libcamera2ndk.so
libmediandk.so  libnativewindow.so  libbinder_ndk.so  libc.so
```

完整列表：`$NDK/.../sysroot/usr/lib/aarch64-linux-android/<api>/`

## 坑 8：LTO 导致的诡异问题

**症状**：

- 编译奇慢
- 链接时报奇怪的符号问题
- 某些代码被"优化没了"

**原因**：`-flto` 在链接时做跨文件优化，行为有时出人意料。

**解法**：调试时先关掉：

```makefile
# 注释掉 -flto
APP_LDFLAGS := -Wl,--gc-sections -s
```

确认问题不是 LTO 引起的，再打开。

## 排查工具：`ndk-build V=1`

所有编译问题，第一步都是看**真实的编译命令**：

```bash
ndk-build V=1 2>&1 | head -30
```

输出：

```
[arm64-v8a] Compile++ : main <= main.cpp
C:/dev/android-ndk-r27c/toolchains/llvm/prebuilt/.../clang++ \
  -MMD -MP -MF obj/.../main.o.d \
  -target aarch64-none-linux-android25 \
  --sysroot=C:/dev/android-ndk-r27c/.../sysroot \
  -std=c++20 -fexceptions -frtti -fvisibility=hidden \
  -I jni/include -I jni/include/ImGui ... \
  -c jni/src/main.cpp -o obj/.../main.o
```

对照检查：
- `-target` 对不对（架构 + API）
- `--sysroot` 路径对不对
- `-I` 有没有你的头文件目录
- `-std` 是不是你想要的
- 你加的 `-D` 宏在不在

## 动手：故意制造并修复 4 个坑

```bash
# 坑 A：ABI 错。编译一个 32 位的推到 64 位设备
ndk-build APP_ABI=armeabi-v7a
adb push libs/armeabi-v7a/app /data/local/tmp/app32
adb shell /data/local/tmp/app32        # 观察报错

# 坑 B：缺 include 路径
# 在 Android.mk 里注释掉一行 LOCAL_C_INCLUDES，重新编译

# 坑 C：STL 冲突
# 改 APP_STL := c++_shared 但没把 libc++_shared.so 推上去

# 坑 D：缺库
# 在 Android.mk 里去掉 -llog，代码里还用 __android_log_print
```

每个都记录：报错原文、你怎么判断原因、怎么修。
