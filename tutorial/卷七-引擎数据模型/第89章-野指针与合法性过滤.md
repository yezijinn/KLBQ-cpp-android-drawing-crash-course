# 第 89 章 · 野指针与合法性过滤

> [!abstract] 本章目标
> 建立一套完整的防御体系，让程序在读错数据时**不崩溃**。
> 这是外部程序稳定运行的生命线。

## 先看"野指针"从哪来

```cpp
uint64_t obj = dr->Read<uint64_t>(arrayAddr + i * 8);
```

这个值可能是：

| 情况 | 值 |
|---|---|
| 正常 | 一个有效的 Actor 地址 |
| 读取失败 | 0 |
| 对象已释放 | 原地址，但内存已被回收/复用 |
| 偏移失效 | 完全随机的数 |
| 数组越界 | 相邻数据被当指针 |

**后面四种都是"野指针"，用它去读就可能崩溃。**

## 本项目原有的过滤

```cpp
static bool IsValidObject(uint64_t address) {
    return address > 0x10000000ULL && address < 0x10000000000ULL &&
           (address % 4) == 0;
}
```

三条判据。但**不够**——下面逐条分析并扩展。

## 第一层：地址范围

```cpp
bool InUserRange(uint64_t addr) {
    // Android arm64 用户空间典型范围
    return addr > 0x10000000ULL && addr < 0x10000000000ULL;
}
```

依据（第 17 章的布局）：
- 小于 0x10000000（256MB）：几乎不可能是堆/库地址
- 大于 0x10000000000（1TB）：超出用户空间

> [!note] 这些数字怎么来的
> Android arm64 的 `TASK_SIZE` 取决于 `VA_BITS`（通常 39 或 48）：
> - 39 位：用户空间上限 `0x0000007F_FFFFFFFF`（512GB）
> - 48 位：上限 `0x0000FFFF_FFFFFFFF`（256TB）
>
> 本项目的 `0x10000000000`（1TB）是个保守的经验值。
> **要精确就得查设备的 `VA_BITS`**，但经验值够用。

## 第二层：对齐

```cpp
bool IsAligned(uint64_t addr) {
    return (addr % 4) == 0;      // 至少 4 字节对齐
}
```

指针在 C++ 里至少按 4 字节对齐（多数是 8）。
奇数地址必然是错的。

更严格：

```cpp
bool IsAligned8(uint64_t addr) { return (addr % 8) == 0; }
```

## 第三层：读权限（maps 校验）

最靠谱但最慢：查这个地址是否真的映射了。

```cpp
class RegionCache {
public:
    void Refresh(pid_t pid) {
        regions_ = GetScannableRegions(ParseMaps(pid));
        // 排序以便二分查找
        std::sort(regions_.begin(), regions_.end());
    }

    bool Contains(uint64_t addr) const {
        // 二分查找
        auto it = std::upper_bound(regions_.begin(), regions_.end(), addr,
            [](uint64_t a, const auto &r) { return a < r.first; });
        if (it == regions_.begin()) return false;
        --it;
        return addr < it->second;
    }

private:
    std::vector<std::pair<uint64_t,uint64_t>> regions_;
};
```

**成本**：每次校验一次二分查找（~20 次比较，纳秒级）。
比读失败导致的异常处理便宜得多。

> [!tip] 缓存要定期刷新
> 进程会 mmap/munmap，缓存会过期。
> 建议每 1~2 秒刷新一次，或者读失败时立即刷新。

## 第四层：值合理性

读出来的**值**本身也要检查：

```cpp
// 坐标：必须是有限数，且在合理范围
bool IsValidPosition(const Vec3 &p) {
    if (!std::isfinite(p.x) || !std::isfinite(p.y) || !std::isfinite(p.z))
        return false;
    // UE4 世界坐标通常在 ±1e6 厘米（10 公里）内
    const float LIMIT = 1e7f;
    return std::fabs(p.x) < LIMIT && std::fabs(p.y) < LIMIT && std::fabs(p.z) < LIMIT;
}

// 数量：不能为负，不能巨大
bool IsValidCount(int32_t c) {
    return c >= 0 && c <= 10000;
}

// 名字 ID：不能为 0（0 是"无名字"）
bool IsValidNameId(uint32_t id) {
    return id != 0 && id < 0x1000000;
}

// 角度：在合理范围
bool IsValidAngle(float deg) {
    return std::isfinite(deg) && deg >= -360.0f && deg <= 360.0f;
}
```

**每个字段都该有对应的合理性判据。**

## 第五层：跨字段一致性

几个字段之间应该自洽：

```cpp
bool IsConsistent(const ActorSnapshot &s) {
    // 有名字 ID 就应该能解析出名字
    if (s.nameId != 0 && s.name.empty()) return false;

    // 有 root 组件就应该有坐标
    if (s.root != 0 && !IsValidPosition(s.position)) return false;

    // .screen 位置与 world 位置应该对应（投影可逆验证太贵，跳过）

    return true;
}
```

## 第六层：结果过滤（绘制前）

即使前面都过了，画之前还要再查：

```cpp
static bool IsFiniteScreenPoint(const Vector2A &point) {
    return std::isfinite(point.X) && std::isfinite(point.Y);
}

if (!IsFiniteScreenPoint(rootScreen) ||
    !IsFiniteScreenPoint(topScreen) ||
    !IsFiniteScreenPoint(bottomScreen)) {
    continue;
}
```

以及包围盒检查（第 52 章）：

```cpp
if (boxWidth <= 1.0f || boxWidth > abs_ScreenX ||
    boxRight < 0.0f || boxX > abs_ScreenX ||
    boxBottom < 0.0f || boxTop > abs_ScreenY) {
    continue;
}
```

## 完整的过滤流水线

```
读指针
  ↓ ① 范围检查
  ↓ ② 对齐检查
  ↓ ③ （可选）maps 校验
处理对象
  ↓ ④ 读字段
  ↓ ⑤ 每个字段的合理性
  ↓ ⑥ 跨字段一致性
投影
  ↓ ⑦ isfinite 检查
绘制
  ↓ ⑧ 屏幕包围盒检查
```

**八层防御，一层都不能省。**

## 一个通用的校验工具

```cpp
struct ValidationResult {
    bool ok;
    const char *reason;
};

class PtrValidator {
public:
    ValidationResult Check(uint64_t addr) const {
        if (addr == 0)
            return {false, "null"};
        if (!InUserRange(addr))
            return {false, "out-of-range"};
        if (!IsAligned(addr))
            return {false, "misaligned"};
        if (strict_ && !regions_.Contains(addr))
            return {false, "unmapped"};
        return {true, nullptr};
    }

    void SetStrict(bool s) { strict_ = s; }
    void Refresh(pid_t pid) { regions_.Refresh(pid); }

    // 统计各原因的拒绝次数（调试用）
    std::unordered_map<std::string, int> stats;

private:
    bool strict_ = false;
    RegionCache regions_;
};
```

统计各原因的拒绝次数——**调试时极其有用**：
如果 "out-of-range" 占 90%，说明偏移错了；
如果 "unmapped" 占多数，说明对象被释放了。

## 性能考虑

| 检查 | 成本 |
|---|---|
| 范围/对齐 | ~1 ns |
| isfinite | ~1 ns |
| 二分查找 maps | ~50 ns |
| 完整校验一个 Actor | ~200 ns |

对比一次内存读取（~3000 ns），**校验成本可忽略**。

**结论：宁可多校验，也不要崩溃。**

## 本项目的防御盘点

| 位置 | 防御 |
|---|---|
| `IsValidObject()` | 范围 + 对齐 |
| 每级指针链后 | `if (X == 0) return;` |
| `IsFiniteScreenPoint()` | isfinite |
| 包围盒检查 | 屏幕范围 |
| `camMakeMatrix` | FOV 范围、NaN 检查、0 值检查 |
| `w < 0.001f` | 近平面 |
| `len > 1024` 检查 | 名字长度上界 |
| `boxWidth > abs_ScreenX` | 异常尺寸 |

**还缺的**（可以做改进）：
- maps 校验（第三层）
- 跨字段一致性（第五层）
- 校验统计（便于诊断）

## 动手：给自己的程序加防御

1. 加 `PtrValidator`，记录各原因的拒绝次数
2. 在 UI 上显示统计（像"信息"页那样）
3. 故意改错一个偏移，看统计怎么变
4. 再故意让 demo 引擎释放一个对象，看是否触发 "unmapped"

**看到统计数字变化，你就有了一个诊断工具**——
以后游戏更新导致偏移失效，一眼就能看出是哪一环出问题。
