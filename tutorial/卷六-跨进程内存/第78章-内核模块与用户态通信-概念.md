# 第 78 章 · 内核模块与用户态通信（概念篇）

> [!abstract] 本章目标
> 理解内核模块是什么、它能做什么、以及用户态怎么跟它说话。
> **本章是概念篇，不写驱动代码**。

> [!note] 承上
> 前几章都是**用户态**方案（process_vm_readv）。
> 本章讲另一条路——**内核模块**能做什么、用户态怎么跟它说话（概念篇，不写驱动）。

## 先看为什么需要内核模块

用户态程序受限于：

| 限制 | 表现 |
|---|---|
| 只能访问自己的地址空间 | 读别人内存要走系统调用 |
| 系统调用有固定开销 | 每次几微秒 |
| 有些能力根本没有 | 硬件断点、绕过页表直接读物理内存 |
| 容易被检测 | `/proc/self/status` 的 TracerPid 等 |

内核模块（`.ko`，Loadable Kernel Module）运行在 EL1：

- 能访问**任意**进程的任意内存
- 能操作页表、寄存器、硬件
- 能提供自定义的系统调用/设备文件
- 用户态几乎无法察觉

**代价**：需要 root + 能加载模块（且内核没锁 `modules_disabled`）。

## LKM 是什么

```c
// hello_module.c（最小内核模块）
#include <linux/module.h>
#include <linux/kernel.h>

static int __init hello_init(void) {
    printk(KERN_INFO "Hello from kernel\n");
    return 0;
}

static void __exit hello_exit(void) {
    printk(KERN_INFO "Bye from kernel\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
```

编译后得到 `hello.ko`，加载：

```bash
insmod hello.ko        # 加载
lsmod | grep hello     # 确认
dmesg | tail           # 看到 "Hello from kernel"
rmmod hello            # 卸载
```

**注意**：Android 上通常需要：
- root
- 内核版本匹配（vermagic 校验）
- 或者禁用模块签名校验

## 四种用户态↔内核通信方式

| 方式 | 机制 | 速度 | 复杂度 |
|---|---|---|---|
| **设备文件** | `open/read/write/ioctl` | 中 | 低 |
| **procfs** | `/proc/xxx` 文件 | 中 | 低 |
| **sysfs** | `/sys/xxx` 属性 | 慢 | 低 |
| **共享内存 + 轮询** | mmap + 标志位 | **最快** | 中 |
| **netlink** | 网络套接字 | 中 | 中 |

**本项目用第四种**（共享内存 + 轮询），因为：
- 延迟最低（无系统调用开销）
- 可以传大块数据
- 实现简单

第 23 章讲过原理，第 79 章讲具体实现。

## 为什么不用 ioctl（它更"标准"）

ioctl 是常规做法：

```c
// 用户态
int fd = open("/dev/mydrv", O_RDWR);
ioctl(fd, CMD_READ_MEM, &args);

// 内核态
static long my_ioctl(struct file *f, unsigned int cmd, unsigned long arg) {
    copy_from_user(&args, (void*)arg, sizeof(args));
    /* 处理 */
    copy_to_user((void*)arg, &args, sizeof(args));
}
```

**每次 ioctl 都是一次系统调用**（几微秒）。
本项目每帧要发几百个请求，累积起来：

```
500 次 ioctl × 3µs = 1.5ms      ← 占 60fps 预算的 9%
```

共享内存方案：

```
用户态写请求 → 置标志 → （内核轮询到）处理 → 置完成标志
无系统调用，开销 = 一次内存写 + 自旋等待 ≈ 1-2µs
```

差距明显。

## 内核模块能做什么（本项目用到的）

| 能力 | 用户态能做吗 | 内核能做吗 |
|---|---|---|
| 读写任意进程内存 | 能（process_vm） | ✓ 更快 |
| 硬件断点 | ✗ | ✓ |
| 触摸注入（更低层） | 能（uinput） | ✓ |
| 虚拟定位 | 部分 | ✓ |
| 陀螺仪伪造 | ✗ | ✓ |
| 系统调用监控 | ✗ | ✓ |
| 隐藏进程/模块 | ✗ | ✓ |
| 修改页表/权限 | ✗ | ✓ |

## 内核里怎么读别的进程内存

几种做法：

```c
// 方法 1：get_task_mm + access_process_vm（推荐）
struct pid *pid_struct = find_get_pid(pid);
struct task_struct *task = get_pid_task(pid_struct, PIDTYPE_PID);
if (task) {
    struct mm_struct *mm = get_task_mm(task);
    if (mm) {
        access_process_vm(task, addr, buf, len, FOLL_READ);   // 读
        mmput(mm);
    }
    put_task_struct(task);
}
put_pid(pid_struct);

// 方法 2：直接走页表（更底层）
// 查 pgd → pud → pmd → pte → 物理页
// 再用 kmap 映射到内核地址空间读写

// 方法 3：copy_from_user（需要先切换到目标进程的地址空间）
kthread_use_mm(target_mm);
copy_from_user(kernel_buf, user_addr, len);
kthread_unuse_mm(target_mm);
```

方法 1 最安全（内核已经封装好了），方法 2 最灵活（能绕过页权限检查）。

## 内核线程

驱动通常创建一个内核线程来处理请求：

```c
static struct task_struct *worker_thread;

static int worker_fn(void *data) {
    while (!kthread_should_stop()) {
        if (req->kernel) {              // 有新请求
            handle_request(req);
            req->kernel = false;
            req->user = true;           // 通知完成
        }
        // 短暂让出 CPU，避免 100% 占用
        schedule_timeout_interruptible(1);   // 或用 cond_resched()
    }
    return 0;
}

worker_thread = kthread_run(worker_fn, NULL, "my_worker");
```

**纯轮询会占满一个 CPU 核**，所以要加 `cond_resched()` 或短暂睡眠。

本项目在用户态侧用 `asm volatile("yield")` 降低功耗（第 23 章），
内核侧同理。

## 风险

> [!danger] 内核模块出错 = 内核崩溃（kernel panic）
> - 空指针解引用 → 整机重启
> - 死循环 → 手机卡死
> - 内存泄漏 → 系统逐渐耗尽
>
> **没有保护机制。** 用户态程序崩溃只是自己挂，内核模块崩溃是系统挂。
>
> 所以：
> 1. 先在虚拟机/QEMU 里测试
> 2. 每个指针都要判空
> 3. 加超时和边界检查
> 4. 准备好救砖方案（fastboot、恢复模式）

## 本教程的边界

## 不需要内核的替代方案

回顾一下，其实大部分能力用户态都有替代：

| 需求 | 用户态方案 |
|---|---|
| 读内存 | `process_vm_readv` ✓ |
| 写内存 | `process_vm_writev` ✓ |
| 触摸注入 | `uinput` ✓ |

| 遮挡判定 | Embree（自己算）✓ |

**本项目的无内核模式（SysHal）就是这么做的**——功能完整，只是性能和隐蔽性略差。

## 动手（概念验证，不写内核代码）

> [!important] 前置条件
> 本节是**用户态概念验证**，可在**任意平台本机跑**——不需要写内核模块、不需要设备。

在用户态验证"共享内存 + 轮询"模型：

```cpp
// 两个进程，一个"模拟内核"，一个"模拟用户态"
// 共享内存结构
struct RequestObj {
    volatile bool kernel;      // 用户态置位：有新请求
    volatile bool user;        // 内核态置位：处理完成
    volatile int  op;
    volatile int  status;
    uint64_t addr;
    uint8_t  data[4096];
    int      size;
};

// 用户态侧
void SendRequest(RequestObj *req) {
    req->op = 1;               // READ
    req->kernel = true;        // 提交
    while (!req->user) { asm volatile("yield"); }   // 等
    req->user = false;         // 消费
}

// "内核"侧（另一个进程）
void ProcessRequests(RequestObj *req) {
    while (running) {
        if (req->kernel) {
            // 处理
            req->status = 0;
            req->kernel = false;
            req->user = true;      // 完成
        }
        usleep(100);               // 避免占满 CPU
    }
}
```

跑起来测一下延迟：**这和在真正的内核模块里通信的模型完全一样**，
只是"内核"换成了另一个进程。

## 课后习题

### 习题 78.1 写一个最小内核模块骨架（★★，应用变式）

**任务要求**：仿照本章的 `hello_module.c`，写一个提供设备文件 `/dev/mydev` 的模块骨架
（只需 `init` 里注册字符设备，`exit` 里注销）。

**参考骨架**：

```c
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/miscdevice.h>

static long mydev_ioctl(struct file* f, unsigned int cmd, unsigned long arg) {
    // 处理请求
    return 0;
}
static const struct file_operations fops = {
    .unlocked_ioctl = mydev_ioctl,
};
static struct miscdevice mydev = {
    .minor = MISC_DYNAMIC_MINOR,
    .name  = "mydev",
    .fops  = &fops,
};
static int __init my_init(void) { return misc_register(&mydev); }
static void __exit my_exit(void) { misc_deregister(&mydev); }
module_init(my_init); module_exit(my_exit);
MODULE_LICENSE("GPL");
```

**验证断言**：`insmod mydev.ko` 后 `ls /dev/mydev` 存在；`rmmod mydev` 后消失。

### 习题 78.2 分析"内核模块的能力与代价"（★★★，分析+评价）

**任务要求**：分析：

1. 内核模块相比用户态方案，**多出哪些能力**？
2. 代价是什么？（至少 3 项）
3. 从工程角度，什么情况下**值得**用内核模块？

**参考答案要点**：
1. 读任意进程内存（不靠系统调用）、硬件断点、绕过页表、更难被检测；
2. 代价：需 root + 加载权限、内核版本强绑定（一升级可能失效）、崩溃会导致**内核 panic**（整机重启）；
3. 当用户态方案**能力不足**（如需要硬件断点/物理内存访问）或**性能不够**（系统调用开销大）时。

> [!tip] 评价层要点
> 内核模块是"**能力换稳定性**"的极端选择：能力最强，风险也最高。
> 判断标准：先问"用户态能不能做"，能就别上内核——**能用上层解决的绝不碰内核**。

## 本章小结

> [!abstract] 本章要点已收束
> 回头把本页的"动手"与结论串成一句话；有勾不上的验收项，回去补做。

> [!danger] 【安全最佳实践】内核模块的权限与风险
> **威胁机制**：
> ① 内核模块运行在**最高特权级**（EL1），一个 bug 可导致整机崩溃或后门；
> ② 加载未签名/未审计的 `.ko` = 把系统控制权交给它；
> ③ 内核模块可绕过 SELinux 等所有用户态防护。
> **规避原则**：
> - **只加载可信来源**的内核模块（自己编译 / 官方签名）；
> - 生产环境开启 **module signature verification**；
> - 优先用**用户态方案**（`process_vm_readv`，第 74 章）——它能覆盖大部分需求；
> - 内核开发**必须**在可恢复的测试设备/模拟器上做。
